# using-daynight Goal 工作流需求

公开 `using-daynight` skill 使用本文的 Goal 讨论与交付协议。
[Agent skill 需求](daynight-agent-skill.md)拥有整体使用与安装要求；本文拥有 Goal 行为，
[架构设计](../design/daynight-goal-workflow.md)拥有机制。

## 目的与范围

需要多个独立交付成果或阶段才能完成的工作，先与用户讨论清楚需求，再讨论具体方案，
经用户确认方案后登记带依赖的实际交付任务。Goal 使用既有 task、`dependsOn`、
`externalDependsOn`、附件和 PR 属性表达，不增加 Goal 专用资源、状态、命令或模式。
feature、bug 修复、架构或设计及拆解出的实际工作项属于任务；Agent 临时生成的读文件、
运行命令和常规检查等执行步骤留在当前任务的执行计划中。

该协议适用于随 npm 发布的 skill 源码。现有四种模式、项目发现、精确版本、任务与附件
错误语义、安装、并发和交付授权规则继续有效。讨论材料在所属 task 的 description 或
附件中保存；向用户请求审阅前读回核验，提供任务和资源引用，修订与确认结果保持同步。
适用条件及长期创建许可由 [Agent skill 要求](daynight-agent-skill.md#as2-必需追踪评审授权与事实来源)拥有。

## 必须交付的行为

| 编号 | 要求 |
|---|---|
| GW1 | 根据工作是否需要多个独立成果或阶段选择普通任务或 Goal，用户无需使用特定关键词。复用前读取已有任务的问题、范围、资料、验收与实际上下文；标题不能证明身份。 |
| GW2 | Goal 首先只创建或复用 `[Goal]<outcome>` 需求讨论任务，正文说明已知问题、目标、范围、约束、UI 适用性、当前待澄清问题与阶段完成条件。此时不创建方案占位任务或交付子任务。每个阶段有自足 description 和包含“方案”“验收标准”的专属主 Markdown；最终需求是讨论产出，不是开始讨论的前提。 |
| GW3 | 用户明确要求开始 Goal 需求讨论时，该请求授权当前讨论任务的创建及 set-status in_progress，使用观察版本执行并核验。若用户只要求登记，唯一的当前阶段任务保持 todo，登记核验后返回，不开始讨论。 |
| GW4 | 需求讨论与用户共同明确完整问题、背景、最终结果、范围、必要行为与约束、排除项和整体验收。当前内容持续写入所属任务，完整细节由其主附件拥有；此阶段不决定具体架构或修改生产实现。 |
| GW5 | UI Goal 在需求讨论中形成最终布局、视觉、交互与代表性状态，并产出纯前端可交互、采用最终样式的 mock UI 及必要资源。覆盖相关的有数据、空、加载、失败、禁用、长内容和窄屏情境；查看并操作原型，不能用静态草图或简化样式替代。 |
| GW6 | 只有用户明确确认当前需求并指示进入方案讨论，例如“可以了，进行架构讨论”，才记录确认内容、核验资料与阶段验收，并用观察版本 set-status done 当前 in_progress 需求任务。确认服务已返回 done 后，才创建或复用方案/架构讨论任务，以普通 dependsOn 依赖已完成的需求任务，并按该明确讨论指令设置为 in_progress。需求讨论完成只表示需求已确认。 |
| GW7 | 方案讨论任务基于已确认需求和适用原型，与用户讨论职责、接口、数据与控制流、边界和失败行为、关键决策、验证方案及候选工作拆分。讨论材料和候选拆分保存在该任务内；用户确认当前方案前，不创建交付子任务。 |
| GW8 | 用户明确确认当前方案后，才登记覆盖完整 Goal 的实际交付子任务及真实依赖。每个子任务有确定身份、问题、范围、交付物、方案、完整验收与验证方法。每个交付任务的 description 直接列出所属架构/方案 task ID 及本任务适用架构文档的完整附件路径；间接后继同样保留这些入口。登记时逐项核验正文引用及实际资料，执行者在实施前读取所列输入。新交付任务保持 todo；方案确认本身不启动执行或开启自动执行许可；已有执行范围继续有效。全部任务、附件与依赖读回核验后，方案讨论任务才满足拆分完成条件并可 set-status done。 |
| GW9 | Goal 内阶段和交付的真实前置使用普通 dependsOn；已核验归其他同项目链所有的前置保留 externalDependsOn 分类。没有其他普通实施前置的交付根直接依赖方案讨论任务，所有交付路径经过方案完成。两类前置均阻塞执行；分类、上游 done 和用户方案确认不扩大执行权限。 |
| GW10 | Goal 创建许可覆盖已确认目标内按阶段发生的登记，无需逐个重复申请，但不允许提前创建未来阶段或未确认方案的交付任务。开始指定讨论阶段的明确指令，仅授权该讨论的 set-status in_progress；创建本身不启动执行，run-task 与 autopilot 沿用已有明确执行范围。交付授权、实现、发布、部署、外部通信、合并及主线 push 保持独立授权。 |
| GW11 | 阶段确认必须对应当前可读材料，并保存在所属任务。确认后发生实质修订，推进前须重新取得用户确认。所有元数据和生命周期操作使用决策时读取的精确版本；附件独立核验。写入部分成功保留原 ID 恢复，不确定结果先读回，不能重复建链、盲目换版本或在前阶段完成尚未确认时创建后阶段。 |
| GW12 | 讨论阶段完成取决于用户确认和自身阶段验收；Agent 判断、独立审查或 CI 不能替代确认。仅因仓库存在 PR 交付规则，不把讨论完成绑定到设计 PR 合并；单独的仓库文档或代码交付继续遵守其 PR 规则，用户明确把 PR 交付列为该讨论的验收时也必须满足。用户明确要求的需求→方案转场可以直接执行，不启动 autopilot；任意交付任务的连续选择仍需明确 autopilot 授权。 |
| GW13 | 只有全部实际交付任务确认完成、必要实现 PR 平台确认合并，且原始 Goal 及已确认变更的整体验收满足，才能报告整个 Goal 完成。终验收记录需求对照结论、证据、缺陷和未验证项；需求 task 的 done、方案 task 的 done、空 ready 页、部分实施结果或辅助脚本通过都不能代替整体验收，不为验收辅助脚本增加 PR 门槛。 |

## 阶段资料与确认

需求讨论任务首先保留已知背景、待澄清问题和讨论方法，逐步形成完整要求。方案讨论任务
仅在需求经确认并完成后创建，首先保留当前设计问题和讨论方法，逐步形成具体方案。
主附件的“方案”和“验收标准”描述当前阶段如何推进、如何确认完成，不声称尚未产生的
结果已经存在。自足 description 使读者不打开附件也能理解当前任务的具体工作。

需求和适用 UI 原型归需求讨论任务；共享架构与候选、最终拆分归方案讨论任务；每个
交付任务只拥有自己的主附件、必要资源和证据。每个交付任务的 description 直接列出
架构/方案 task ID 与本任务需要读取的架构文档完整附件路径；架构文档实际保存在
仓库时，保留所属架构任务身份并使用已核验的不可变仓库引用。对于“架构任务 → A → B”，
B 即使只直接依赖 A，也在自己的 description 保留架构资料入口。资料引用不额外
建立执行依赖，不能仅靠依赖链或 plan.md 中的间接引用代替正文入口。执行者在实施前
读取所列资料；必要输入缺失或不可读时保持未就绪。不得假设 `task://`、跨任务相对
链接、固定服务主机或新 API，不默认复制相同整套材料。独立快照必须记录目的、来源与版本。

请求用户审阅前保存当前完整材料并读回。用户确认时，记录确认对应的材料及阶段结果；
有阻塞性问题或没有明确确认时，讨论任务保持 in_progress。需求确认同时明确要求进入
方案讨论，才产生下一阶段的开始指令；单纯的进度评价或要求继续修改不构成转场。
方案讨论中的任务清单先作为讨论材料，确认后再实际登记。登记失败时仍保留方案任务和
已确认子任务，补齐并读回全部内容后才完成方案讨论。

## 生命周期、交付与恢复

所有任务由 create 产生 todo。明确讨论开始指令授权当前讨论使用精确版本 set-status in_progress；
登记本身不开始执行。普通任务及交付任务在已有明确执行范围内、ready 且阶段资料齐备后开始，
不增加逐任务审批。已授权范围可持续覆盖其就绪后继；状态不扩大实现、部署、发布、外部通信、
合并或主线 push 权限。allowAgents 默认 false，只约束自动发现选择；明确指定的任务队列可采用
手工执行路径，不自动开启该标记。需求/方案确认仍按阶段要求进行，不由 autopilot 代替。

任意三状态对可由 set-status 设置并受版本、权限和依赖保护，重开不表示停止旧执行进程。
讨论转场保持指定身份，不从候选列表自行选取无关任务；autopilot 必须明确启动。

讨论任务按用户确认与阶段验收完成。独立的仓库代码、文档、原型交付以及用户明确纳入
讨论验收的 PR 交付，仍需真实检查、授权合并和平台确认；保留开放 PR 的指令继续有效，
完成要求不授予合并权限。讨论验收与仓库交付分别记录，不能把需求讨论 done 当作原型
已合并，或把方案讨论 done 当作实际实施已经交付。

登记、附件、元数据和状态转换是独立写入，不是事务。任一步骤结果不确定时，读取完整
资源及操作上下文确认实际状态；相似标题或空清单不足以决定重发。需求 set-status done 未确认
之前不创建方案任务；方案后续登记只补齐未完成部分。冲突后重新读取并判断，不能仅
更换版本重放。依赖声明按 CLI 完整替换语义保留普通和外部两类关系，附件内容与元数据
分别确认。当前 ID、工作位置、阻塞、等待和下一步使用已有执行检查点。

## 验收与证据边界

Goal 拆分中的终验收必须明确覆盖原始整体需求及已确认变更后的组合交付，遵守
[Agent skill 的终验收要求](daynight-agent-skill.md#终验收任务)和随包
[Final acceptance](../../packages/daynight/src/commands/skill/skills/using-daynight/SKILL.md#final-acceptance)
规则。它统一规定可用方法、临时辅助脚本与开发交付的区别，以及整体结论和证据的
完成条件。下表列出本协议自身的验证，任一工具或部分检查通过不能替代完整 Goal 验收。

| 检查 | 必须观察到的结果 |
|---|---|
| 独立情境审查 | 覆盖普通任务、仅登记 Goal、开始需求讨论、未确认需求不得建方案任务、用户确认并转场、开始方案讨论、确认前只有候选拆分、确认后登记 todo 子任务、架构 → A → B 中 B 的正文架构资料入口与实施前读取、必要资料不可读时不实施、实质修订须重确认、独立验收任务、UI 原型、阶段 PR 例外、实际依赖、部分写入、精确版本冲突、不确定状态写入、非 autopilot 的明确讨论转场、交付授权与整体验收；无未处理的 Critical/Major。 |
| 静态资料 | 入口 frontmatter、四份模式引用及共享协议、所有实际本地链接、英文发布内容、阶段要求和授权一致；active 文档及决策所有者同步。 |
| 实际任务资料 | 逐项读取自足正文、当前主附件与真实共享来源，确认具体工作、阶段确认、材料身份、实际内容与引用相符，逐项核验每个交付正文的架构任务和适用文档入口；不以附件数量或统一链接包代替语义检查。 |
| 构建与打包 | 既有资源复制和链接检查及实际 build、npm pack 证明完整协议随包发布；复制内容与源码一致，安装覆盖和 scope 规则继续有效。 |
| 工具门禁 | 根据实际改动运行 CLI typecheck、test、build 和所需 CI，检查新增文件、文档链接、note 结构与 git diff --check。 |
| 整体验收 | 对实际交付的源码和包身份记录 commit、版本与产物 hash，核对发布 bundle 的 GW1–GW13 行为及完整任务范围；安装文件证据、指令情境审查和平台合并事实分别报告。 |

情境审查检查指令是否一致、阶段能否执行，不证明任意模型必然遵循。复制和隔离安装
证明文件及安装操作，不证明讨论或交付已经执行。既有模拟 launcher 验收覆盖三个
Agent 与两个 scope，不运行真实 Agent 或模型、不发布 npm、不部署。协议不增加后台
组件、数据库格式或运行时调度，已有任务与附件命令继续由原有套件验证。
