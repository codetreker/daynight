# 本仓库 Goal 工作流需求

本仓库 `development-workflow` 使用本文的 Goal 讨论与交付协议。
[Agent skill 需求](daynight-agent-skill.md)拥有整体使用与安装要求；本文拥有 Goal 行为，
[架构设计](../design/daynight-goal-workflow.md)拥有机制。

## 目的与范围

需要多个独立交付成果或阶段才能完成的工作，先与用户讨论清楚需求，再讨论具体方案，
经用户确认方案后登记带依赖的实际交付任务。Goal 使用既有 task、`dependsOn`、
`externalDependsOn`、附件和 PR 属性表达，不增加 Goal 专用资源、状态、命令或模式。
feature、bug 修复、架构或设计及拆解出的实际工作项属于任务；Agent 临时生成的读文件、
运行命令和常规检查等执行步骤留在 session 执行计划中，不成为 task 或任务材料。

该协议适用于本仓库开发工作。普通执行与实际 Worker assignment、项目发现、精确版本、任务与附件
错误语义、安装、并发和交付授权规则继续有效。需求讨论 task 除 description 外必须拥有
完整 `spec.md` 附件；设计和拆分成果保存在各自所属 task。向用户请求审阅前读回核验
当前完整成果及必需资源，提供任务和资源引用。
成果随修订同步，讨论方法、确认经过与操作授权留在 session。
适用条件及长期创建许可由 [Agent skill 要求](daynight-agent-skill.md#as2-必需追踪评审授权与事实来源)拥有。

## 必须交付的行为

| 编号 | 要求 |
|---|---|
| GW1 | 根据工作是否需要多个独立成果或阶段选择普通任务或 Goal，用户无需使用特定关键词。复用前读取已有任务的问题、范围、资料、验收与实际上下文；标题不能证明身份。 |
| GW2 | Goal 首先只创建或复用 `[Goal]<outcome>` 需求讨论任务，正文说明已知问题、目标、范围、约束、UI 适用性、当前待澄清问题与阶段完成条件。此时不创建方案占位任务或交付子任务。每个阶段按共享任务定义与成果标准提供自足内容，description 明确当前责任和来源，正文或实际引用提供目标、范围、输入、交付物与验收；最终需求是讨论产出，不是开始讨论的前提。 |
| GW3 | 用户明确要求开始 Goal 需求讨论时，该请求授权当前讨论任务的创建及 set-status in_progress，使用观察版本执行并核验。若用户只要求登记，唯一的当前阶段任务默认保持 proposed，除非使用方明确选择 todo，登记核验后返回，不开始讨论。 |
| GW4 | 需求讨论与用户共同明确完整问题、背景、最终结果、范围、必要行为与约束、排除项和整体验收，形成所属任务的完整 `spec.md` 附件。description 保留自足任务说明及该附件入口；spec 应让未参与聊天的读者独立理解完整需求，适用内容及完整性见下文。当前成果随讨论同步，详细内容保留单一拥有位置，讨论方法、确认过程和操作授权留在 session；此阶段不决定具体架构或修改生产实现。 |
| GW5 | UI Goal 在需求讨论中形成最终布局、视觉、交互与代表性状态，并产出纯前端可交互、采用最终样式的 mock UI 及必要资源。覆盖相关的有数据、空、加载、失败、禁用、长内容和窄屏情境；查看并操作原型，不能用静态草图或简化样式替代。数据与交互状态仅保存在当前页面内存，禁止 localStorage、sessionStorage、Cookie、IndexedDB 及其他本地持久状态变更，依赖库也不得间接持久化；刷新或重新打开恢复初始状态，详见仓库流程 create-task 的原型要求。 |
| GW6 | 必须先上传并读回完整当前 `spec.md` 及必需资源，向用户提供需求 task ID 和附件路径；只有用户明确确认该 spec 并指示进入方案讨论，例如“可以了，进行架构讨论”，才核验当前内容与阶段验收，在需求任务仍 in_progress 时创建或复用普通 dependsOn 依赖它的方案/架构任务，新建时显式使用 `--status todo`，保持后继 todo，并读回完整任务、资料和依赖。该必要后继登记核验完成后，才用观察版本 set-status done 需求任务；确认服务已返回 done 后，再按明确讨论指令启动架构任务。登记失败或结果未确认时，需求任务保持 in_progress，保留已有 ID 恢复。Managed 入口可在已有创建授权覆盖的已确认范围内登记并读回必要后继，但只完成原 claim 并返回 controller，不开始或执行后继；缺少创建授权或必要内容时保持未完成，沿既有人类介入流程处理。需求讨论完成只表示本阶段成果和必要后继登记均满足。 |
| GW7 | 方案讨论 task 的 description 直接注明需求 task ID、完整 `spec.md` 附件路径及适用原型来源，实际读取已确认 spec 和所需资源后，与用户讨论职责、接口、数据与控制流、边界和失败行为、关键决策、所需验证能力及候选工作拆分。当前设计成果和候选拆分保存在该任务内，讨论和评审方法留在 session；用户确认当前方案前，不创建交付子任务。 |
| GW8 | 候选交付拆分在方案确认前须满足下文的拆分质量要求；用户明确确认当前方案后，才登记覆盖完整 Goal 的实际交付子任务及真实依赖。每个子任务有连贯且可独立判断完成的成果、清晰责任和可审查边界，以及确定身份、真实必需输入和交付物。每项必须具体说明服务 Goal 的目标、scope 范围、实施方案和验收，均须与已确认 Goal 及方案一致；实施方案包含选定方案、详细设计和带变更目标及预期结果的有序实施步骤，不留待执行者继续调研以选择方案或补完设计。不要求 session 执行安排或单独方案文件。每个交付任务的 description 直接列出所属架构/方案 task ID 及每个必需来源：来源 description 全文或其中适用章节、真实附件的完整路径，或保留所属任务身份的不可变仓库引用；间接后继同样保留这些入口。登记时逐项核验正文引用及实际资料，执行者在实施前读取所列输入。新交付任务显式用 `--status todo` 创建；方案确认本身不启动执行或开启自动执行许可；已有执行范围继续有效。全部任务、附件与依赖读回并重新核验各任务四项内容与边界、整组覆盖和衔接后，方案讨论任务才满足拆分完成条件并可 set-status done。 |
| GW9 | Goal 内阶段和交付的必要直接前置使用普通 dependsOn；已核验归其他同项目链所有的前置保留 externalDependsOn 分类。没有其他普通实施前置的交付根直接依赖方案讨论任务，所有交付路径经过方案完成。登记前按仓库流程 dependencies 的传递去冗余规则省略已有其他保留路径覆盖的直接边；每次创建、替换或清空依赖后必须调用 task graph 读取实际依赖图，核验必要路径完整且无冗余，断边后的各连通分量与必要图外路径分别读取，读取失败或路径未验证时不能报告通过。普通边只能由全普通路径替代，外部路径不能取代普通设计门禁，独立前置及保留边分类不变。两类前置均阻塞执行；分类、上游done/cancelled终态和用户方案确认不扩大执行权限。 |
| GW10 | Goal 创建许可覆盖已确认目标内按阶段发生的登记，无需逐个重复申请，但不允许提前创建未来阶段或未确认方案的交付任务。开始指定讨论阶段的明确指令，仅授权该讨论的 set-status in_progress；创建本身不启动执行，普通和 managed 指定执行沿用已有明确范围。交付授权、实现、发布、部署、外部通信、合并及主线 push 保持独立授权。 |
| GW11 | 阶段确认必须对应当前可读材料，需求确认明确针对完整 spec 内容；被接受的成果及有效状态保存在所属任务，确认经过和操作授权留在 session。任一阶段成果确认后发生实质修订，推进前须重新取得用户确认；需求修订还须同步完整 spec、相关 description 与适用原型。附件变更不改变 task version，不能仅凭该版本断定内容仍被确认。所有元数据和生命周期操作使用决策时读取的精确版本；附件独立核验。写入部分成功保留原 ID 恢复，不确定结果先读回，不能重复建链或盲目换版本；必要后继未登记核验时不完成前阶段，前阶段完成尚未确认时不启动后阶段。 |
| GW12 | 讨论阶段完成取决于用户确认和自身阶段验收；Agent 判断、独立审查或 CI 不能替代确认。仅因仓库存在 PR 交付规则，不把讨论完成绑定到设计 PR 合并；单独的仓库文档或代码交付继续遵守其 PR 规则，用户明确把 PR 交付列为该讨论的验收时也必须满足。用户明确要求的普通需求→方案转场可以直接执行，但不授权任意后继或实际交付；managed 执行完成或等待后返回 controller，不开始或执行后继阶段。 |
| GW13 | 只有全部实际交付任务确认完成、必要实现 PR 平台确认合并，且原始 Goal 及已确认变更的整体验收满足，才能报告整个 Goal 完成。终验收记录需求对照结论、支持结论所需的关键观察、缺陷和未验证项；全部成员done/cancelled仅表示调度已结束，取消不证明需求已交付；需求 task 的 done、方案 task 的 done、空 ready 页、部分实施结果或辅助脚本通过都不能代替整体验收，不为验收辅助脚本增加 PR 门槛。 |

## 阶段资料与确认

需求讨论任务首先保留已知背景、待澄清需求问题、预期成果和完成条件，逐步形成完整要求。
方案讨论任务仅在完整 spec 经确认且用户明确要求转场后创建，先作为仍在进行的需求
任务的 todo 后继登记并核验；需求任务完成确认后才开始设计，首先保留当前设计问题、输入和交付目标，
逐步形成具体方案。共享任务定义与成果标准由仓库流程 `references/task-content.md` 拥有。
正文直接提供、引用文档和混合组织均可；任务定义描述当前阶段要交付什么及怎样算完成，
不声称尚未产生的结果已经存在。当前讨论如何开展、工具选择及 session 的执行或验证安排属于 session。
description 说明当前任务及其责任，并提供准确可读的资料入口；未指定附件交付时，正文内容完整无需主附件。Goal 需求阶段的完整 `spec.md` 是必需附件，不能由正文替代；managed 的按类型附件及设计多方独立评审、无 Critical/Major 与另附非阻塞问题 review 文件的门槛，由仓库流程 [Complete delivery standard](../../.agents/skills/development-workflow/references/delivery.md#worker-delivery-results) 拥有，正文不能替代其必需附件。
缺少 session 命令安排、工具选择或临时调试计划不能成为拒绝阶段启动或移交的理由；Goal 交付任务必需的选定方案、详细设计和有序实施步骤属于任务内容，不受此豁免。明确产出需求或设计的阶段仍按自身要求形成成果，不能据此把尚未设计完成的交付任务视为已就绪。

需求讨论 task 的 `spec.md` 独立承载完整要求，至少说明背景与问题、目标与非目标、适用
角色和场景、所需行为与边界、约束、成功与失败行为，以及可观察的整体验收标准。
权限、数据生命周期、平台和非功能要求按实际目标的适用性说明，不制造无关栏目。
影响范围、行为或验收判定的开放问题须在需求确认前解决，具体架构选择留给方案阶段。
涉及 UI 时，spec 引用已上传且实际可交互的最终样式纯前端原型及必要资源。description
保留目标、当前责任、范围、交付物、完成条件与 spec 入口，不重复完整规范；初始
brief 可以尚不完整，完整 spec 是结束需求讨论的成果要求。

完整 spec 和适用 UI 原型归需求讨论任务；共享架构与候选、最终拆分归方案讨论任务；交付
任务只拥有自己的任务定义、必要资源和实际成果。最终验收结论及支持结论所需的关键
观察属于成果，确认经过、CI/review/merge 过程与恢复上下文不进入任务材料。
每个交付任务的 description 直接列出
架构/方案 task ID 及本任务需要读取的实际来源。共享内容在来源任务正文时，明确
description 全文或其中适用章节，通过 `task show <source-task-id> --json` 读取；真实
附件文档列完整附件路径；仓库文档保留所属架构任务身份并使用已核验不可变引用。
正文内容不需要编造路径，也不要求复制或迁移为附件。对于“架构任务 → A → B”，
B 只直接依赖 A，沿链继承架构前置，并在自己的 description 保留架构资料入口。
资料引用不额外建立执行依赖，不能仅靠依赖链或附件中的间接引用代替正文入口。执行者在实施前
读取所列资料；必要输入缺失或不可读时保持未就绪。不得假设 `task://`、跨任务相对
链接、固定服务主机或新 API，不默认复制相同整套材料。独立快照必须记录目的、来源与版本。

请求用户审阅前上传当前完整 spec、核验实际读回内容和必需资源，再提供需求 task ID、
`spec.md` 附件路径与当前稿。上传失败、附件不可读或内容不完整时，不满足需求阶段验收。
用户确认时，在 session 核对确认对应的实际内容，任务保存被接受的成果及阶段结果；
有阻塞性问题或没有明确确认时，讨论任务保持 in_progress。需求确认同时明确要求进入
方案讨论，才允许登记该下一阶段。先读回后继及真实依赖，再完成并核验需求任务，最后
按该明确指令开始方案讨论；单纯的进度评价或要求继续修改不构成转场。
方案讨论中的任务清单先作为讨论材料，确认后再实际登记。登记失败时仍保留方案任务和
已确认子任务，补齐并读回全部内容后才完成方案讨论。

## 交付拆分质量

每个候选及已登记的 Goal 交付任务都必须具有四项具体内容，由仓库流程 [Delivery task brief](../../.agents/skills/development-workflow/references/goal.md#delivery-task-brief) 拥有：目标说明服务哪个已确认 Goal 要求或结果及自身贡献；scope 说明负责的行为、修改边界与相关排除项和上下游责任；实施方案提供本任务所承担部分的选定方案及理由、实际所需详细设计和有序实施步骤，明确变更目标、预期结果、组件责任、契约及必要集成顺序，足以直接实施，不留待执行者调研以选择方案或补完设计；验收提供可观察的成功、失败与边界行为、验证方法、预期结果及适用阈值，证明本任务对 Goal 的贡献。

四项可直接写在正文或由准确可读的引用提供，不强制标题或独立文件。description 必须具体说明本任务的贡献与边界，并直接定位其余内容的适用来源章节；只写“按架构实现”、笼统指向整个 Goal 或复制整套材料均不足。共享细节保持单一归属。实施方案及必要实施步骤是持久任务内容，具体就绪标准由仓库流程 [Task content standard](../../.agents/skills/development-workflow/references/task-content.md#definitions-and-results) 统一拥有；session 的命令安排、工具活动与调试过程仍留在 session。正常代码阅读、局部编码选择、实现调试和验证属于执行工作，不能代替未完成的任务定义或实质设计。需求和方案讨论的自身设计仍是阶段产出。

Goal 拆分边界同样由仓库 Goal 协议拥有：每项围绕一个可独立判断完成的成果，完成该成果所需的修改放在一起，独立目标分开。按成果目的与可审查性判断粒度，不规定固定任务、文件、行数或工时，也不强制统一切分方式。文件、技术层或常规执行步骤本身不足以成为拆分理由；有明确独立成果的基础能力、迁移或验收可以单独成项。

[Goal breakdown](../../.agents/skills/development-workflow/references/goal.md#register-the-delivery-breakdown) 另核对整组任务：共同覆盖已确认行为和验收，明确集成与整体验收归属，解决工作遗漏、责任重叠或冲突，核对生产者与消费者的产物、接口、失败行为、验收及实际必要依赖。独立任务描述齐全不能单独证明整组完整；具有独立结果的验收才需要单独任务。

方案确认前逐项核验候选任务的目标、范围、实施方案和验收与已确认 Goal 及待审方案一致；登记读回时按已确认 Goal、范围和方案再次核验实际四项内容，阻止偏离 Goal 的工作。存在缺口时方案任务保持 in_progress；实质改变已确认方案须重新确认。Handoff 复核所选任务的四项内容及其真正必需的引用和上下游契约，任务定义和实施设计未完成、缺少详细设计或实施步骤、偏离 Goal 都是具体缺项；前置尚未实现时，已定方案、设计、契约及集成步骤仍须足以界定当前工作；它不重新证明整个 Goal 覆盖，也不自行重分任务或改变依赖；具体处置由 [AS11](daynight-agent-skill.md#as11-handoff-的移交审查) 拥有。

## 生命周期、交付与恢复

任务由 create 默认产生 proposed，内部已确认的方案后继和交付子任务显式创建为 todo。明确讨论开始指令授权当前讨论使用精确版本 set-status in_progress；
登记本身不开始执行。普通指定任务及交付任务在已有明确执行范围内、全部前置满足且阶段资料齐备后，可从 proposed 或 todo 直接进入 in_progress，
不增加逐任务审批。已有明确执行范围继续有效，普通 skill 不因此自行选择或连续推进后继；状态不扩大实现、部署、发布、外部通信、
合并或主线 push 权限。allowAgents 默认 false，只约束自动发现选择；普通明确指定的任务可采用
手工执行路径。创建、拆分与调度不自动开启该标记；明确移交授权下的 handoff 按
[移交审查要求](daynight-agent-skill.md#as11-handoff-的移交审查)审查后启用，移交不替代
阶段确认、真实依赖或执行授权。需求/方案确认仍按阶段要求进行，不能由执行器的判断代替。

set-status保持原三态转换并提供不可恢复的cancelled终态，均受版本和权限保护。取消满足依赖但不证明阶段结果或Goal交付；重开不表示停止旧执行进程。
普通讨论转场保持指定身份，不从候选列表自行选取后继。Worker 使用实际 assignment 的运行约束和原 claim，不套用普通开始或完成流程，也不开始或执行后继阶段。共同任务输入、交付、成果和验收准备由仓库流程 `references/task-execution.md` 拥有，阶段要求由本文拥有。

完成任务必须同时满足自身成果和已确认范围内必要后继的登记核验；登记不启动后继，
也不授予额外创建或执行权限。无实际后续工作的终端任务不制造后继或临时执行步骤。
Managed 可在已有创建授权内登记已确认的必要后继，包括方案 assignment 要求的交付
拆分，但不开始或执行后继。缺少创建授权或必需内容时，沿既有人类介入流程补齐。
managed 确需用户介入时，按仓库流程 [Request user interaction](daynight-worker.md#w-08人工介入与强制撤回) 先核验原 assignment，以观察版本将自己任务设为 paused=true 并回读确认，再输出问题、保存 Session 等待上下文并退出循环，保持 in_progress。用户自由选择回应方式；反馈后核验原 assignment、问题已解决及授权允许恢复，解除暂停并回读确认后继续原任务，未解决则保持暂停。失败、冲突和未知结果遵守 write-safety，普通 CI/review 等待不触发该暂停，不选择其他任务或执行后续阶段。

讨论任务按用户确认与阶段验收完成。独立的仓库代码、文档、原型交付以及用户明确纳入
讨论验收的 PR 交付，仍需真实检查、授权合并和平台确认；保留开放 PR 的指令继续有效，
完成要求不授予合并权限。讨论验收与仓库交付分别记录，不能把需求讨论 done 当作原型
已合并，或把方案讨论 done 当作实际实施已经交付。

登记、附件、元数据和状态转换是独立写入，不是事务。任一步骤结果不确定时，读取完整
资源及 session 操作上下文确认实际状态；相似标题或空清单不足以决定重发。必要后继未登记并读回核验之前，当前任务不能 set-status done；需求完成结果未确认
之前不启动方案任务。方案或交付子任务部分登记后只补齐未完成部分。冲突后重新读取并判断，不能仅
更换版本重放。依赖声明按 CLI 完整替换语义保留普通和外部两类关系，附件内容与元数据
分别确认。当前 ID、工作位置、操作授权、阻塞、等待和下一步使用 session 或已有本地执行检查点，
不为恢复写入 task 描述或附件，缺失授权不能从任务材料推断。

## 验收与证据边界

Goal 拆分中的终验收必须明确覆盖原始整体需求及已确认变更后的组合交付，遵守
[Agent skill 的终验收要求](daynight-agent-skill.md#终验收任务)和仓库流程
[Final acceptance](../../.agents/skills/development-workflow/references/final-acceptance.md)
规则。它统一规定可用方法、临时辅助脚本与开发交付的区别，以及整体结论和证据的
完成条件。下表列出本协议自身的验证，任一工具或部分检查通过不能替代完整 Goal 验收。

| 检查 | 必须观察到的结果 |
|---|---|
| 独立情境审查 | 覆盖普通任务、仅登记 Goal、开始需求讨论、description 完整但缺 spec、spec 上传失败或不可读、未确认 spec 不得建方案任务、用户确认当前 spec 后先登记 todo 架构后继再完成需求、后继登记失败保持需求 in_progress、已有后继复用、终端任务无需制造后继、确认旧内容后覆盖附件须重确认、方案正文缺需求来源或来源不可读不得开始设计、开始方案讨论、确认前只有候选拆分、确认后登记 todo 子任务、架构 → A → B 中 B 的正文架构资料入口与实施前读取、必要资料不可读时不实施、实质修订须重确认、独立验收任务、UI 原型、阶段 PR 例外、实际依赖、部分写入、精确版本冲突、不确定状态写入、普通指定讨论转场、managed 完成/等待后返回、公共手册、仓库流程与 Worker 运行约束的职责分离、交付授权与整体验收；无未处理的 Critical/Major。 |
| 拆分质量情境 | 核验候选与已登记任务的目标、范围、实施方案和验收均紧贴 Goal，识别方案尚未选定、详细设计或有序实施步骤缺失、笼统架构链接、待执行者调查决定实现、验收不能证明 Goal 贡献、单项内容漂移、无关目标混装、按文件或技术层机械拆分、范围过大或过碎、遗漏与重叠责任、未定义上下游契约，以及集成或整体验收无归属；允许有明确结果的基础能力、迁移与独立验收任务，以及契约已充分定义但前置尚未完成的任务。移交只核验选定任务，不借质量检查扩大到整组重分或无关发现。 |
| 静态资料 | 仓库流程入口 frontmatter、共享执行与内容标准及 Goal 协议、所有实际本地链接、英文发布内容、阶段要求和授权一致；active 文档及决策所有者同步。 |
| 实际任务资料 | 逐项读取正文、其当前必需引用、已产生成果与真实共享来源，确认各任务四项内容与边界、具体工作、阶段完成门槛、材料身份、实际内容与引用相符，逐项核验每个交付正文的架构任务和适用文档入口，并检查整组覆盖、责任与交付衔接；不以附件数量或统一链接包代替语义检查。 |
| 构建与打包 | 资源复制和链接检查及实际 build、npm pack 证明公共手册随包发布且与 CLI 输出同源；仓库流程独立可读，安装覆盖和 scope 规则继续有效。 |
| 工具门禁 | 根据实际改动运行 CLI typecheck、test、build 和所需 CI，检查新增文件、文档链接、note 结构与 git diff --check。 |
| 整体验收 | 对实际交付的源码和包身份记录 commit、版本与产物 hash，核对发布 bundle 的 GW1–GW13 行为及完整任务范围；安装文件证据、指令情境审查和平台合并事实分别报告。 |

情境审查检查指令是否一致、阶段能否执行，不证明任意模型必然遵循。复制和隔离安装
证明文件及安装操作，不证明讨论或交付已经执行。既有模拟 launcher 验收覆盖三个
Agent 与两个 scope，不运行真实 Agent 或模型、不发布 npm、不部署。协议不增加后台
组件、数据库格式或运行时调度，已有任务与附件命令继续由原有套件验证。
