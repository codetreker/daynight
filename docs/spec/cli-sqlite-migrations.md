# CLI SQLite 数据库格式升级需求

## 范围与版本

CLI 在访问已有本地业务数据库时检查其格式，并在必要时自动升级后完成原操作。查询命令同样适用；不要求用户额外运行迁移命令。帮助、补全、配置登记和只读环境探测仍不打开业务数据库。

每个数据库由所属 store 选择自己的 SQL 目录，文件名决定该库迁移序列，只使用本库的 `PRAGMA user_version` 记录格式版本。版本与 CLI 包版本分开，不同数据库可以使用相同编号。新建、版本 0 重置和从受支持非零版本升级的数据库必须得到相同目标格式。

| 数据库 | 路径 | 当前版本与受支持非零来源 |
|---|---|---|
| Review 状态 | `~/.daynight/state.sqlite` | 当前 2，保留已有 1→2 转换 |
| Worker 认领索引与清理调度 | `~/.daynight/worker/state.sqlite` | 当前 12，版本 5 保留原行升级，6→7 移除清理通知步骤字段，版本 12 冻结 claim 原生配置，旧详细库 1–4 明确拒绝 |
| Web 执行状态 | `~/.daynight/worker/web-executions.sqlite` | 当前 3，1→2 移除 cleanup 的重复字段；2→3 新增独立编排阻塞表 |
| Controller journal | `~/.daynight/controller/executions/<execution-id>/journal.sqlite` | 当前 9，保留 1→5 转换、5→6 正文导出、7 图片账本、8 不可变内容指针和 9 输入来源 |
| Native resume lease | `~/.daynight/controller/native-resume-leases.sqlite` | 当前 1 |

上述五个业务库的 `user_version=0` 统一表示重置：通过既有业务准入后，丢弃该文件内原有用户 schema 和数据，再从本库基线及按文件名排序的全部后续升级重建。此规则包含已有空文件和任意无版本表，不检查其是否匹配历史 schema，也不解析旧 JSON 来决定是否保留。查询访问已有版本 0 文件时同样执行重置并返回重建后的结果。

各库的建库与 SQL 升级由所属目录顶层的 SQL 文件决定。加载器以大小写不敏感的 `.sql` 后缀发现候选，只接受合规的小写命名和普通文件，忽略无关非 SQL 文件及普通辅助目录。合规文件按名称字典序执行，至少三位且目录内同宽的数字前缀就是版本号；首文件是基线，后续版本必须逐一连续，增加合规编号文件会自动进入迁移链，不再维护逐步 TypeScript 注册表。目录缺失、空 SQL 链、非法 SQL 候选、重复版本或中间缺号明确失败。版本必须为正的 32 位有符号整数，Worker 以 `005-baseline.sql` 保持基线 5。

五个基线及其连续编号升级组成各库主链；无版本来源参考和条件接入 SQL 不属于运行资源。JSON 转换、业务准入、事务及 user_version 推进继续由 TypeScript 负责。发布包必须完整复制源码 SQL 目录，资源读取失败在打开用户数据库前暴露，不能回退到内联 DDL。无效 SQL 在参考构造或实际执行边界失败，实际迁移仍遵守单库回滚保证。没有独立清单时，不声称能识别一个保持连续的目录是否缺少原本的末尾文件；当前目标版本取实际发现链的末尾，资源完整性检查核对实际源码与发布产物。

纯实例锁 SQLite gate 没有业务格式，不加入迁移序列。Worker gate 与其 `state.sqlite` 共用文件，gate 已创建但尚无业务表的版本 0 文件同样重建。文件创建许可只决定缺失文件能否创建，不决定已有版本 0 文件能否初始化；缺库语义保持各入口原有行为。

## 数据保留与原子性

已知、有效的非零版本升级覆盖表、索引、约束和已存储 JSON 的格式变化，并保留有效记录、业务含义、原生会话、操作身份、发布结果、恢复与清理责任。升级不能重置未知结果或伪造完成、停止及输入受理证据。版本 0 的 schema 和数据明确不保留；非零未知、较新或不受支持的版本保留原库并拒绝访问，Worker 1–4 仍属于拒绝范围。

一次打开所需的重置、基线建库和连续迁移在同一 `BEGIN IMMEDIATE` 事务中完成，SQL 结构、数据和 `user_version` 一起提交或回滚。重置不得删除或替换数据库文件。迁移失败或进程中断后，重新打开只接受完整旧格式或完整目标格式；修复实际原因后可再次打开。各数据库分别保证原子性，不承诺跨文件事务；Worker 所需任一库打开失败时不启动协调业务。

Review v2 不为接入公共机制额外提高版本或改写记录；journal v6 的版本变化来自会话正文转文件归档，原非零历史必须先可靠导出再删除正文表。Web 的清理记录自 v2 起只保留 kind、startedAt、deadline；原生操作身份仍由执行记录持有，回执从 Controller journal 读取。1→2 迁移移除旧重复字段，保留其余业务记录，不在当前代码兼容旧清理步骤表示。Web 2→3 新增编排阻塞表并保留原执行记录，已升级的库拒绝旧二进制访问。版本 0 重置不成为非零版本的历史数据清洗路径。

## 查询与并发

当前格式的查询在同一个只读快照中检查版本并读取数据，不为迁移取得实例锁或额外写权限。运行中的 writer 可以继续提交；查询仍读取自己的已提交快照。SQLite 自身打开既有 WAL/SHM 所需的权限不因该约束改变。

需要重置或升级的查询先结束并关闭读取连接，经领域准入完成迁移，再重开只读快照、检查当前格式并执行原查询。数据库在检查后消失时不得被重新创建；最终快照遇到较新版本、未知非零结构或再次回到旧格式时明确失败，不无限重开。

缺库语义由原读取入口决定：Review listing 和 Controller snapshot 的明确缺失可为空；Controller operation 缺文件仍失败，缺行才为空。权限、损坏、异常父路径和一般打开错误不能冒充缺库。

每次非零来源检查读取的版本和结构必须属于同一快照，包括可写打开时的初检；不能把不同提交中的 user_version 和 schema 拼在一起，将有效的并发升级误判为格式损坏。版本 0 初检只标识重置，不要求匹配历史结构。初检的短读取事务结束后，才能配置连接的持久设置或取得写事务。重置或迁移仍须在实际写事务中重读版本及必要结构，不沿用初检结果，不重复执行已经提交的步骤。迁移不得绕过现有业务所有权：

- Review/Worker 纯维护不接管任何已有实例锁，包括死 PID、损坏元数据或未知归属。自己的迁移连接未确认关闭时保留维护锁；只释放自己创建且身份仍匹配的锁。
- Controller 可写 journal 阶段必须持有原 execution 的存储 permit，内部复用同一 permit，拒绝跨 journal、伪造或释放后的许可。只有明确 ESRCH 可接管陈旧存储 owner；活跃、权限、格式或未知存活保留原锁。迁移在实际连接上绑定本次 permit 和预留写入检查，当前格式纯读取不取锁、不访问迁移 context；旧格式文件读取才申请维护，借用连接必须显式绑定原 permit。任何 DDL 之前检查旧 writer：版本 0 没有 `execution` 表时可重置；已有该表时必须能读取 `id` 和 `owner_pid`，列损坏或活跃、无法确认的 owner 阻止重置。非零版本继续执行已有 owner 检查。纯格式处理不认领 writer、不推进 generation、不将进程消失解释成完整原生停止。停止记录持同一 permit 在事务外验证原进程边界，并在提交前比较 snapshot、ticket_hash 和 owner_pid 未变。升级、已停止维护与 writer 准入分别保留其角色约束；本机阶段关闭句柄后释放，网络期间不持锁。
- Resume 库已有 lease 表的任何保留行都阻止重置或迁移，不按过期或 PID 消失回收；没有 lease 表的版本 0 文件可重置。当前格式下不同 native key 的租约仍可并存。

## 失败与可观察结果

不支持的非零版本或来源、必要结构缺失和无效数据都必须明确失败，保留数据；程序不降级或猜测修复。SQL、JSON、权限、磁盘、锁等待、提交、回滚及关闭失败保留实际原因和错误链。非空版本 0 重置可在 BEGIN 前临时关闭连接外键，每次实际重置都必须在提交前通过 `foreign_key_check`，成功提交后在返回连接前恢复及核实原设置；空版本 0 初始化和非零迁移保持原设置。已提交的事务不因后续外键设置恢复、诊断或关闭失败而变为回滚，也不能因此重跑迁移；外键恢复失败作为清理错误报告已提交结果并关闭连接。

Resume lease 申请只有成功返回后才能用于启动新的原生执行。首次建库或重置时，本次 INSERT 已明确提交但完成诊断失败、申请未返回且原连接已确认关闭的，可以用新的既有文件连接检查当前格式并清理本次 native_key+nonce 对应的租约。只允许处理本次已知归属；不存在该行可确认无遗留，nonce 已替换、提交结果未知或关闭未确认时保留记录。原诊断错误继续抛出，清理也失败时聚合两者；这不构成陈旧 lease 的回收规则。

数据库失败不能被 IPC 不可达分支吞掉、触发替代 Controller 或重放输入。独立 Controller 退出时仍尝试停止自己已启动的进程；无法读取 journal 时保留错误，不伪造停止证明、归档结果或 native lease 释放条件。

诊断说明数据库、阶段、可识别的源/目标版本、迁移步骤和事务结果；版本 0 转换报告为 `reset`。原始错误可在内存保留，文本和 JSONL 输出不得包含业务 JSON、prompt、token 或原始 SQL 参数。完全没有格式检查的旧二进制不提供并发混跑或降级安全保证；首次切换需退出相关旧实例，保留无法确定的归属证据。

## 验证边界

真实 SQLite 来源 fixture 覆盖五库新建、已有空版本 0 文件、任意版本 0 schema 和坏 JSON 重置、已知非零迁移及未知非零来源拒绝。重置验证包括外键、trigger、view、虚拟表及其外部内容表，检查原 schema、数据和版本在失败后一起保留。独立进程验证并发 writer 与中断重开；检查实际记录、索引和版本，不能只检查异常文本。当前格式 WAL 读取、旧锁和 owner/lease 保留、关闭/回滚双失败，以及 Controller 停止与 IPC 错误边界分别验证。
