# CLI SQLite 数据库格式升级需求

## 范围与版本

CLI 在访问已有本地业务数据库时检查其格式，并在必要时自动升级后完成原操作。查询命令同样适用；不要求用户额外运行迁移命令。帮助、补全、配置登记和只读环境探测仍不打开业务数据库。

每个数据库由所属 store 明确选择自己的迁移序列，只使用本库的 `PRAGMA user_version` 记录格式版本。版本与 CLI 包版本分开，不同数据库可以使用相同编号。新建和从受支持来源升级的数据库必须得到相同目标格式。

| 数据库 | 路径 | 当前版本与受支持来源 |
|---|---|---|
| Review 状态 | `~/.daynight/state.sqlite` | 当前 2，保留已有 1→2 转换 |
| Worker 认领索引 | `~/.daynight/worker/state.sqlite` | 当前 5，接入已知无版本六列或七列最小索引；旧详细库 1–4 明确拒绝 |
| Web 执行状态 | `~/.daynight/worker/web-executions.sqlite` | 当前 1，接入已有无版本表及其已支持的 JSON 契约 |
| Controller journal | `~/.daynight/controller/executions/<execution-id>/journal.sqlite` | 当前 5，保留已有 1→5 转换 |
| Native resume lease | `~/.daynight/controller/native-resume-leases.sqlite` | 当前 1，接入已有无版本结构；保留 lease 阻塞迁移 |

纯实例锁 SQLite gate 没有业务格式，不加入迁移序列。Worker gate 与其 `state.sqlite` 共用文件，合法建库入口必须能初始化 gate 已创建但尚无业务表的数据库。已有空业务文件只能由允许建库的入口初始化；查询不得将它伪装成已初始化的空结果。

## 数据保留与原子性

升级覆盖表、索引、约束和已存储 JSON 的格式变化。有效记录、业务含义、原生会话、操作身份、发布结果、恢复与清理责任必须保持，不能因升级重置未知结果或伪造完成、停止及输入受理证据。

一次打开所需的连续迁移在同一数据库事务中完成，SQL 结构、数据和 `user_version` 一起提交或回滚。迁移失败或进程中断后，重新打开只接受完整旧格式或完整目标格式；修复实际原因后可再次打开。各数据库分别保证原子性，不承诺跨文件事务；Worker 所需任一库打开失败时不启动协调业务。

当前 Review v2 和 journal v5 不为接入公共机制额外提高版本或改写记录。已知 Worker 七列索引和 Web 无版本库的版本登记保留原业务数据；Web 接入不借解析器的已有缺省字段处理重写 JSON 字符串。旧详细 Worker 库不新增迁移路径，也不自动删除。

## 查询与并发

当前格式的查询在同一个只读快照中检查版本并读取数据，不为迁移取得实例锁或额外写权限。运行中的 writer 可以继续提交；查询仍读取自己的已提交快照。SQLite 自身打开既有 WAL/SHM 所需的权限不因该约束改变。

需要升级的查询先结束并关闭读取连接，经领域准入完成迁移，再重开只读快照、检查当前格式并执行原查询。数据库在检查后消失时不得被重新创建；最终快照遇到较新版本、未知结构或再次回到旧格式时明确失败，不无限重开。

缺库语义由原读取入口决定：Review listing 和 Controller snapshot 的明确缺失可为空；Controller operation 缺文件仍失败，缺行才为空。权限、损坏、异常父路径和一般打开错误不能冒充缺库。

每次来源检查读取的版本和结构必须属于同一快照，包括可写打开时的初检；不能把不同提交中的 user_version 和 schema 拼在一起，将有效的并发升级误判为格式损坏。初检的短读取事务结束后，才能配置连接的持久设置或取得写事务。迁移仍须在实际写事务中重读版本和结构，不沿用初检结果，不重复执行已经提交的步骤。迁移不得绕过现有业务所有权：

- Review/Worker 纯维护不接管任何已有实例锁，包括死 PID、损坏元数据或未知归属。自己的迁移连接未确认关闭时保留维护锁；只释放自己创建且身份仍匹配的锁。
- Controller 在任何 DDL 之前检查旧 writer。活跃或无法确认的 owner 阻止迁移；纯升级不认领 writer、不修改 generation，也不将进程消失解释成完整原生停止。
- Resume 库有任何保留 lease 时阻止迁移，不按过期或 PID 消失回收。当前格式下不同 native key 的租约仍可并存。

## 失败与可观察结果

不支持的版本或来源、必要结构缺失和无效数据都必须明确失败，保留数据；程序不降级、删库或猜测修复。SQL、JSON、权限、磁盘、锁等待、提交、回滚及关闭失败保留实际原因和错误链。已提交的事务不因后续诊断或关闭失败而变为回滚，也不能因此重跑迁移。

Resume lease 申请只有成功返回后才能用于启动新的原生执行。首次建库或接入时，本次 INSERT 已明确提交但完成诊断失败、申请未返回且原连接已确认关闭的，可以用新的既有文件连接检查当前格式并清理本次 native_key+nonce 对应的租约。只允许处理本次已知归属；不存在该行可确认无遗留，nonce 已替换、提交结果未知或关闭未确认时保留记录。原诊断错误继续抛出，清理也失败时聚合两者；这不构成陈旧 lease 的回收规则。

数据库失败不能被 IPC 不可达分支吞掉、触发替代 Controller 或重放输入。独立 Controller 退出时仍尝试停止自己已启动的进程；无法读取 journal 时保留错误，不伪造停止证明、归档结果或 native lease 释放条件。

诊断说明数据库、阶段、可识别的源/目标版本、迁移步骤和事务结果。原始错误可在内存保留，文本和 JSONL 输出不得包含业务 JSON、prompt、token 或原始 SQL 参数。完全没有格式检查的旧二进制不提供并发混跑或降级安全保证；首次切换需退出相关旧实例，保留无法确定的归属证据。

## 验证边界

真实 SQLite 来源 fixture 覆盖五库新建、已知起点、现有迁移、SQL/JSON 保留和未知来源拒绝。独立进程验证并发 writer 与中断重开；检查实际记录、索引和版本，不能只检查异常文本。当前格式 WAL 读取、旧锁和 lease 保留、关闭/回滚双失败，以及 Controller 停止与 IPC 错误边界分别验证。
