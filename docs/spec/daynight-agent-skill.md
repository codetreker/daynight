# Agent 项目任务管理 Skill 需求

公开入口为随 `@codetreker/daynight` 发布的 `using-daynight` skill，包含 `handbook`、
`create-task`、`handoff`、`run-task`、`autopilot` 五种内部模式。本文拥有使用、安装与覆盖的可观察
要求；机制由[设计](../design/daynight-agent-skill.md)拥有。既有
[客户端需求](daynight-project-task.md)与[附件需求](daynight-task-attachments.md)
继续拥有命令、项目发现、版本和附件操作语义。

[Goal 流程要求](daynight-goal-workflow.md)拥有整体问题定义、架构设计与实际任务拆分、
实施及整体验收的阶段规则。普通任务与 Goal 阶段共同采用六项内容标准，description
明确当前任务的责任和资料入口；正文与实际引用资料共同提供完整内容。正文完整时无需
主附件，共享资料保留唯一所有者，任务确认与交付证据在当前任务内有明确落点。

## AS1. 发布产物与路由

产品只发布一个公开 `using-daynight` skill。英文 `SKILL.md` 使用标准 frontmatter，
与 `references/handbook.md`、`references/create-task.md`、`references/run-task.md`、
`references/handoff.md`、`references/autopilot.md`，以及共享 `references/task-content.md`
和 `references/goal.md` 一起包含在 npm 安装产物中。
Codex、Copilot CLI、Claude Code 使用相同内容。安装后不依赖源码仓库、仓库内部工作流 skill、未发布文档或包外临时文件；
npm 包移动、升级或卸载不使已安装资源失效。

五种模式是 skill 的使用协议，不增加 CLI 子命令。Agent 根据用户请求和实际上下文路由：

| 模式 | 职责与完成边界 |
|---|---|
| `handbook` | 列出命令用途，解释项目发现、并发更新等背景规则；具体用法查询 CLI help。 |
| `create-task` | 在明确创建许可内复用或登记具体工作；Goal 首先只登记需求讨论任务。仅登记请求核验后返回，明确开始讨论时按 Goal 协议进入当前阶段。 |
| `handoff <task-id>` | 在明确移交授权内读取任务和必需资料并审查，通过后按精确版本启用许可；结果核对后返回，不开始执行。完整要求见 AS11。 |
| `run-task <task-id>` | 执行明确任务；讨论按用户确认与阶段验收，交付按其实际交付条件完成。Goal 的明确用户转场由共享协议处理。 |
| `autopilot <目标或范围>` | 在已授权范围内逐个选择任务并调用 `run-task`，完成后继续。 |

直接调用 `using-daynight` 而没有附加输入时，Agent 根据当前请求与上下文判断模式；
上下文不足或存在歧义时询问用户意图。不能固定进入 handbook，也不能凭候选存在推断
执行意图。只有用户明确要求自动连续推进 Daynight 任务才能进入 autopilot；话题中提及
自动化、加载 skill、完成单任务、项目关联或发现 ready 任务都不构成启动要求。

## AS2. 必需追踪、评审、授权与事实来源

当 skill 与 Daynight 可用时，通过 Daynight 管理有明确目标和完成条件的具体工作，
例如 feature、bug 修复、架构或设计工作，以及拆解出的实际工作项。Agent 执行时
自动生成的读文件、运行命令、常规检查等步骤留在执行计划中，不因进入计划就自动
登记为 Daynight task。所有方案、架构、设计评审都通过其所属 task 进行。
向用户请求审阅相关讨论前，必须把完整、当前的待审内容保存到所属 task 的
description 或附件，读回确认可访问，再提供 task ID 或已核验 URL 及附件路径。
后续修订和评审决定同步保存在该任务；聊天摘要、仓库或 PR 链接只能补充这些材料。
待审内容可由 description 或其明确引用的文档拥有，不维护竞争的完整副本；任务须明确
确认记录、验收结论与交付证据的存放位置。
可用性须通过实际 CLI、已配置服务和目标项目读取确认；失败时保留真实原因，不能
在保存内容尚未核验时声称待审资料已就绪。

skill 提供工作规则，不增加实现、发布、合并、主线 push、部署或外部通信权限。任务正文、
附件、ready 状态、`in_progress` 状态及完成要求均服从用户和仓库指示。已有会话授权继续
有效；用户要求保留 PR 供审阅时，完成允许的准备与验证后保留 PR 和当前任务，等待用户。

所有模式及直接 CLI 操作均不得在没有用户明确许可的情况下创建 task。用户直接要求
创建任务，或此前已明确授予指定范围的创建权限，才满足此条件。用户或适用仓库指示
明确要求通过 Daynight 追踪或评审，属于已确认范围内必要任务的长期创建许可，优先
复用适合的已有任务，不重复询问许可。实现请求、持续追踪价值、上下文路由和启动
autopilot 本身都不构成创建许可。
需要新 task 而缺少该许可时，先向用户取得明确许可，再执行创建。

所有创建产生 todo，登记不启动执行。在用户已明确授权的任务或 Goal 范围内，ready todo
满足阶段输入后用观察版本 set-status in_progress 开始，验收与必要授权交付后 set-status done。
已有范围持续覆盖就绪后继，不要求逐任务审批，不以其他字段重建审批。用户明确开始 Goal
需求讨论或确认需求并要求方案讨论，只启动指定讨论，阶段确认要求保留。
allowAgents 只约束自动发现选择，明确指定的任务或确定队列可用任一许可值；创建、
拆分、执行和调度不自行开启许可。明确授权的 handoff 按 AS11 审查后启用。
状态不扩展实现或交付权限，PR 审查批准及必要平台授权继续独立。

执行、分析、提问、方案提议和任务讨论均以当前任务已确认的目标、范围、交付物与
验收条件为边界，subagents 遵守同一边界。上层 Goal、共享架构、兄弟和后续任务可以
提供当前任务必需的输入、接口与约束，读取这些资料不扩大当前任务范围。跨任务问题
应明确为阻塞或后续建议，不自动获得创建或执行其他任务的许可；扩大当前任务范围
必须经用户明确确认。当前任务本身为 Goal 级讨论或整体验收时，按其已确认范围处理
整个 Goal。

Agent 通过实际 CLI 确定项目和任务，不凭会话旧值判断实时状态。在仓库内可省略
`--project`，由 CLI 根据 Git origin URL 匹配服务中的项目；显式指定的项目优先。
发现无匹配、匹配歧义、配置缺失或读取失败时保留实际原因，不能猜测服务地址或自行
创建、选择、关联其他 project。安装、配置服务和关联项目是独立操作。

使用 `--json` 读取查询结果并保持 ID、状态、描述、精确版本的含义。不能直接编辑关联
文件、使用未公开接口或用临时计划替代服务事实。set-status 是带版本的状态设置，
不提供 assignee 独占锁或可续期租约。并发协调仍需核对实际工作和检查点。

## AS3. handbook 的规则所有权

handbook 保持为命令用途索引与操作背景说明。索引只列命令名称及用途；参数、选项、
输出格式和完整调用方法以已安装 CLI 的 `--help` 为准，不在 handbook 重复示例或
逐项用法，也不暴露本地绑定文件和忽略规则等内部实现。其他模式按需读取它，现有 CLI
与附件规范继续拥有完整命令契约。

背景规则应说明项目定位的使用方式与失败处理。ready 是有界候选，
创建顺序不表达相关性，空结果不能证明没有进行中或被阻塞的工作。list 读取全部匹配
分页，默认排除 `done`；需要包含已完成任务的完整清单或核对历史登记时必须显式包含
已完成任务，对应选项由 CLI help 说明。文本列表是摘要；JSON 列表仅省略
`description`，其余 task 字段保留。需要描述时读取 show，ready、详情和写入结果
保留完整 task 资源。列表按状态和 readiness 分组，不表达相关性。graph 是紧凑
依赖视图，不能替代包含描述、属性和版本的任务详情；图超限后仍可使用有界查询与
指定任务读取。

元数据更新及 set-status 必须携带决策时实际读取的精确版本，不能依赖临提交前的默认读取来保护旧判断，
也不能截断或舍入 int64。描述、依赖和 PR 列表按整个字段替换，保留仍需的数据；冲突
后重新读取并判断变更，而非仅更换版本重放。状态与 readiness 不提供所有权或锁。`allowAgents` 是自动执行许可，独立于状态与 ready；新任务为 false，明确指定的任务执行可处理两种许可值。自动选择只接受许可为 true 的新候选；worker 和自动执行流程不能自行启用，handoff 只在用户明确移交授权内处理。

任务详情不包含附件清单；附件读写独立于任务版本、状态和更新时间。多个文件操作
独立，文件内容与元数据可能部分改变；任务版本不能充当附件版本。写入结果不确定时
先读回核对，create 需结合完整字段与操作上下文确认任务身份，附件需核验实际内容；
不能凭标题匹配、空清单或元数据就假定写入结果。保留真实错误与资源标识，不盲目重发。

## AS4. create-task 的资料与完整性

create-task 首先确认用户已明确许可创建任务，包括适用的长期追踪或评审指示。
feature、bug 修复、架构或设计工作及拆解出的实际工作项，按自身目标、范围与可观察
完成条件创建或复用 task。方案、架构或设计评审使用所属 task。Agent 临时生成的
执行步骤留在已有执行计划中，不自动拆成持久任务。独立验收或验证工作有自身交付
成果时可以作为 task；交付当前任务时运行的常规检查属于该任务的执行步骤。
先读取已有任务的正文、范围、附件与验收目标判断是否可复用，标题相似不证明重复。

普通单成果工作使用一个任务；多个独立交付成果或阶段使用 Goal。Goal 首先只登记
`[Goal]<outcome>` 需求讨论任务，不预建方案占位或交付任务。明确开始讨论的指令
授权当前阶段 set-status in_progress；用户只要求登记时保持 todo 并返回。Goal 范围内
许可覆盖后续按确认顺序发生的登记，不允许提前创建未来阶段或未确认方案的子任务。

| 内容 | 所在位置 |
|---|---|
| 当前任务身份、责任与资料入口 | task 的 Markdown `description` |
| 目标与要求、范围与交付物、方案与设计、输入与输出契约、验收标准与验证方法、资料 | description 直接提供、引用明确拥有文档，或两者混合；每项内容只有一个拥有位置 |
| 用户确认、验收结论与交付证据 | 当前任务明确指定的 description 或本任务附件 |
| 共享 Goal 要求、架构和拆分 | 来源任务的拥有文档，由实际 task ID 与完整附件路径或已核验的不可变仓库引用读取 |
| 前端原型及必要资源 | 拥有原型的任务附件，后继引用真实来源 |
| 实际依赖及性质 | task 的完整 dependsOn 及其 externalDependsOn 子集 |
| PR URL 与 title | `properties.pullRequests` |
| 当前执行位置、阻塞、等待事项和下一步 | 会话或项目已有的执行检查点 |

共享 `references/task-content.md` 拥有六项内容标准，创建、Goal 拆分、handoff 和执行
共同读取。格式按实质内容判断，不要求六个固定标题、重复文档或专属主附件。目标与要求
明确当前问题和期望行为；范围与交付物界定责任；方案与设计说明当前阶段做法和必要
决定；输入与输出契约说明实际来源、消费者、入口、结构、语义、可用时点及验证方式，
无任务间交换时明确说明；验收给出可观察条件、适用失败/边界和验证方法；资料定位
真实来源及适用部分。正文使用 Markdown，按需使用标题、段落、列表、引用、代码块、
表格、链接和图片，不写执行流水。必要进一步引用必须实际读取并避免循环读取；
缺关键内容、不可读引用、任务范围不明或资料/上下游契约冲突不能视为完整。
文件名以实际引用为准，完整前置由 dependsOn 表达，externalDependsOn 保留明确外部子集。
同链前置为普通，经内容核验归其他同项目链所有的成果可标记外部；完成状态、标题或图入口不决定性质。
顶层只表示没有普通前置，外部前置仍阻塞执行且不扩大权限。CLI 任一依赖选项重建完整两类集合，
更新需读取并保留仍需关系；不为视觉归组创建虚构前置。

Web 按 CommonMark/GFM 阅读描述，原始 HTML 作为文本；API 与 CLI 保持原始字符串，
不增加格式标记。完整替换正文时保留 Markdown 语法、换行、代码和仍然有效的资料引用。
描述中的相对链接与图片以当前任务附件根为基准，Markdown 附件内部引用仍以文件目录
为基准；路径不得越出任务根，保留实际大小写与资源身份。上传并确认内容可读后才加入
真实引用。只有任务确实拥有这些文件时才使用 `[方案与验收](plan.md)`、
`[交互原型](mockui/index.html)` 等写法；共享原型继续引用来源任务，产生原型的 Goal
阶段不能在产出前宣称该文件已存在。Web 的导航和 URL 规则由
[任务阅读要求](daynight-task-inspection.md)及[附件要求](daynight-task-attachments.md)拥有。

按当前任务实际需要上传资料。每个 Goal 交付任务的 description 直接列出架构/方案
task ID 及本任务适用架构文档的完整附件路径；即使通过实施前置间接依赖架构任务也
保留这些入口。架构文档在仓库时保留所属架构任务身份并使用已核验的不可变引用。
登记时逐项读回核验，执行前读取所列资料，必要输入缺失或不可读时不开始实施。共享
资料保持单一所有权，不假设新 URL 协议或跨任务相对链接，也不为资料引用增加执行
依赖。确需独立快照时记录原始来源、来源版本与复制目的。

阶段输入不能反向要求本阶段的产出。需求讨论从当前 brief 开始，与用户明确完整
问题、范围、行为、排除项、整体验收及适用原型，不决定具体架构或修改生产实现。
用户确认需求并要求进入方案讨论后，先 set-status done 需求 task 并确认 done，再创建、
set-status in_progress 依赖它的方案 task。方案及候选拆分先在该任务内讨论；用户确认
当前方案后，才实际登记带依赖的交付子任务，上传并读回全部资料。实施根依赖方案
task，方案完成须用户确认及实际拆分核验均满足。详细规则由 [Goal 要求](daynight-goal-workflow.md)拥有。

UI Goal 的描述阶段产出最终视觉样式、可纯前端交互的 mock UI，覆盖相关的主要数据和
空、加载、失败、禁用、长内容、窄屏等状态，资源相对引用可用。实施任务开始时读取并
操作适用的已完成原型；普通前端实施任务同样需要可读的最终样式交互原型作为输入。

创建或复用、设置依赖、上传并更新真实引用后，读回正文、字段、共享输入与当前必需
附件。仅登记的任务及新交付子任务保持 todo；资料完整本身不启动执行。明确讨论开始
指令启动当前阶段，后继沿用已有明确执行范围。部分成功保留原 ID 补全；不确定写入先核对，
仅登记请求核验后返回。公开skill保留任务语言及等价英文标题支持；具体仓库或会话的文档语言指示继续适用。

### 终验收任务

创建或拆分终验收工作时，必须明确被核验的是整个已约定任务或 Goal、其需求来源及
已确认变更，交付需求对照结论、支持证据、缺陷和未验证项。独立验收的成果是该整体
判断；实施阶段已有检查是输入，辅助脚本完成或通过不能代替尚未满足或未验证的要求。
完整规则由随包 [Final acceptance](../../packages/daynight/src/commands/skill/skills/using-daynight/SKILL.md#final-acceptance)
拥有，创建、Goal 拆分、执行与完成入口共同遵守。

可以人工验证、复用已有检查或编写临时辅助脚本。终验收辅助脚本不得提交仓库、集成到
测试、fixtures、runner、CI 或 tooling，不把持续验证系统列为验收交付物，也不增加
辅助脚本 PR 门槛。关于辅助脚本的评审意见不扩大这一范围。必要的实现 PR 仍按实际
交付要求核验；正常实现和已授权缺陷修复保留单元、集成、回归测试及仓库检查，用户
明确要求的长期测试或自动化能力仍按其已确认开发范围交付。

## AS5. run-task 的执行与完成

run-task 接收指定 ID，读取正文及其必需引用、当前任务证据位置和真实共享输入，按所属阶段判断
必需资料；适用原型已经是输入时查看和操作。开始分析、提问或提出方案前，明确当前
任务已确认的范围和验收条件，执行与讨论共同遵守 AS2 的范围约束。澄清与设计以阶段
brief 开始，当前阶段尚待产出的完整要求、UI 或架构不能反过来阻止启动。ready todo
在依赖、阶段输入及已有明确执行范围齐备后使用 task set-status in_progress 和观察
版本开始，核验结果再工作。
显式指定任务或既定队列不要求 allowAgents=true；自动发现候选仍要求 true。
已有 in_progress 核对工作与检查点后恢复；done 按实际结果处理，重开须属于用户明确工作范围，
并遵守前置/后继保护。输入缺失或依赖未完成时保留实际问题，不凭标题补出方案。

Goal 讨论阶段按用户确认和自身阶段验收完成；确认前保持 in_progress，不能由 Agent
判断、review 或 CI 替代。仅因仓库存在 PR 交付规则，不把讨论完成绑定到设计 PR 合并。
独立代码、文档或原型交付，以及用户明确纳入讨论验收的 PR 交付，仍按目标仓库规则
验证、独立审查并维护完整 PR 属性；全部必要 PR 经平台确认合并且验收满足后才 done。
代码完成、PR 创建、review 或 CI 成功不能替代实际交付。通过多个 PR 时逐一确认。

执行前按已确认的交付目的识别[终验收任务](#终验收任务)，再选择验证方法。无需代码
或 PR 的终验收按整体要求、可读结论及证据完成；发现缺陷时如实记录，修复遵守已有
授权和正常交付要求。必需结果仍未满足或未验证时，不得报告整个任务或 Goal 已验收。

完成前将用户确认、结果与必要证据写入本任务指定的正文或附件位置；实际 PR 交付保留 merge
commit 引用。再读取 task，以实际版本 set-status done 并核验服务结果。必要交付 PR 仍打开
或未满足明确的阶段 PR 验收时保持 in_progress，保存等待事项和下一步。no-merge 指令
继续约束实际交付，不能用讨论 done 冒充仓库交付完成；完成规则不授予合并权限。

run-task 一次处理指定任务。普通 CI、review 或合并等待仍属于当前任务；subagents
协作同一任务。需要外部介入时保留实际状态并返回。Goal 中用户明确确认需求并要求
下一讨论时，共享协议可完成当前阶段并开始指定的方案讨论；这不启动 autopilot，也不
选择任意后继。其他完成后返回调用方。身份来自已有检查点，任意 in_progress 项不
代表归本会话所有。

## AS6. autopilot 的串行调度

autopilot 必须有用户明确启动要求，沿用确认的目标与授权范围。先刷新检查点中的当前
任务；若身份未知，按需查询 in-progress 清单并核对上下文，不能任意认领。无当前任务
时，用 `task ready --allow-agents true --json` 读取有界候选，从许可开启且属于授权范围的 ready `todo` 中比较问题、范围、方案、验收及依赖，选择与已授权目标最相关的一个，刷新详情与附件后进入 run-task。补充候选清单继续保留许可筛选；进行中的既定任务按已有检查点恢复，不因候选筛选被替换。

每个会话一次只推进一个任务，候选页不构成批量开工指令。等待交付及 subagent 协作
期间保持当前任务。只有确认 done 才继续选择下一项；遇到需要外部介入的阻塞时保留
当前任务和下一步，交回用户，不能自动换做无关工作。

Goal 需求或方案讨论完成只代表该阶段完成。未获用户明确确认时继续等待当前讨论，
autopilot 不能代替确认、提前建方案任务或提前登记交付子任务。明确的用户讨论转场
由 Goal 协议处理，不要求或激活 autopilot。整个 Goal 仍须全部实际交付和原始整体验收
满足，不能由某个上游 done 推断。

ready 为空或当前页没有匹配项时，按需补充范围相关查询，区分范围完成、依赖阻塞、
其他工作进行中和候选不足。没有观察完整范围时不能宣称全部完成。需要登记缺失的
工作时，必须有用户明确的 task 创建许可，适用的长期追踪或评审指示也满足该条件；
autopilot 执行授权本身不包含该许可。取得或
确认已有许可后遵守 create-task。新任务为 todo，登记不开始执行；已有明确范围可继续覆盖其 ready 后继。
自动发现仅选 allowAgents=true 的 ready todo；确定队列沿用手工路径，流程不自行开启许可。

自动发现先观察真实执行环境 process.platform：win32→windows、darwin→macos、linux→linux，WSL的Linux运行时仍为linux。
未知或不支持时等待，不从任务要求、配置、外层宿主或服务端推断。ready与补充list都携带allowAgents=true和
--compatible-platform <actual-platform>，筛选先于分页，不本地丢弃有界页。自动选出的ID保留自动模式与实际平台上下文，
进入in_progress前重读完整任务，复核todo/ready/许可=true/平台null或匹配，以该完整读取的精确版本设置状态。
资格变化重新选择，执行环境变化重新观察平台；不能把自动选出的ID当成人工指定。用户明确指定的任务或固定队列保留
手工路径，可接受任一许可或平台值，仍受依赖、阶段资料及原执行范围约束，不自行启用许可。

## AS7. 交互安装与 scope

入口保持 `daynight skill install`。按原生命令查找规则检测 `codex`、`copilot`、
`claude`，包含 PATH，以及 Windows 当前目录和 PATHEXT；不启动 launcher，不检查
登录或账号，也不以已有目录判断可用性。仅显示检测到的 Codex、Copilot CLI、Claude Code，
多选初始为空且至少选择一项，再统一选择 User 或 Project，默认 User。无可用 Agent
明确失败。终端不可用时在写入前失败并提示交互终端。无非交互安装参数。

安装不要求服务配置、可达性、origin 或项目关联。帮助和参数错误不检测、不交互、
不读取服务配置、不访问服务、不写文件。安装前取消、EOF 或预检失败无安装副作用；
首次写入前取消也不能留下目录，stage 期间取消清理本次 stage 和新建且仍为空的父目录。

## AS8. 覆盖、旧名称迁移与失败

每次安装完整替换选定 `using-daynight` 叶节点，成功目标全部路径和字节与当前 bundle
相同；移除本地修改和旧文件，不合并、不备份。目标自身为符号链接时只替换链接，
保留原指向对象；父级根目录链接沿用，共享物理根去重写入并保留逐 Agent 结果。

新 bundle 成功发布后，清理同一所选物理 skill 根目录中的旧 `daynight` 叶节点，旧
叶节点为符号链接时同样不跟随。不能提前删除旧入口，不能改动另一 scope、其他物理
根、共享根目录或无关 skill。规划时将安装与旧名称清理涉及的拥有路径一并检查；
严格祖先/后代冲突在任何写入前拒绝并列出目标，避免安装或清理删除其他目标。

目标按确定顺序串行执行。每个 Agent 的完整成功须在新 bundle 发布及旧名称清理完成
后报告，标明 Agent、scope、路径和包版本。所有目标完成才整体成功。任一目标失败
立即停止后续目标并非零退出，区分已成功、失败、未执行；不跨目标回滚或静默重试。

新发布后旧目录清理失败时保留可用新 bundle，如实报告旧入口仍存在或清理状态未确认，
不能声称全部迁移完成。覆盖已有 using-daynight 时删除后 rename 失败可能使目标缺失；
诊断保留阶段、路径、实际原因及清理错误链，不能保证未观察到的旧内容仍在。
成功后提示重新发现 `using-daynight`，包括 Copilot 的 `/skills reload` 和
`/skills info using-daynight`，以及各宿主适用的重载方式。

## AS10. CLI 更新时同步已安装 skill

`using-daynight`；CLI 已是当前或领先版本时也执行同步，以便重试上次 skill 失败。
检测 User 和调用目录所属 Git worktree 的 Project 位置，Agent 路径沿用 AS7。
子目录、linked worktree、submodule 均定位自身根；仓库外只检测 User，不搜索其他
仓库、不登记安装 registry，也不要求 Agent launcher 可用或运行 Agent。

存在的 `using-daynight` 目录或叶节点符号链接视为已有安装，包括入口丢失的目录及
悬空叶链接；缺失叶节点保持缺失。普通文件或其他非目录叶节点、父目录损坏及权限错误

不得触发检测或同步。自动同步没有交互选择，也不能首次安装缺失 skill。

## AS11. handoff 的移交审查

用户明确要求移交指定任务或确定的一组任务，才授权 handoff 进行内容审查并在通过后
启用自动选择许可；自动发现、创建或方案拆分本身均不构成该授权。审查者只凭任务和
明确引用的持久资料判断，不能依赖发起者的聊天、记忆、私人工作区或未继承的会话许可。

读取完整任务、精确版本、状态、许可、平台、真实依赖和 worker 信息，以及必要资料与
执行必需的进一步引用。按六项内容及当前阶段判断充分性，核对适用上下游契约。当前
阶段产出的设计或用户确认不是它自身的启动输入；实现任务的必要设计和约定接口必须
已足以界定接续工作。缺项或未决决定给出具体原因，不补造要求、方案或验收阈值。对
尚未启用的 todo，可在已有确认和授权范围内整理说明与来源，重新审查受影响内容。

| 当前情况 | 必须行为 |
|---|---|
| todo、false、审查通过 | 完成资料更新及读回，核对可变引用后，用最终审查所依据的精确版本设置 allowAgents=true；可同时提交最终 description。真实依赖尚未完成不妨碍预先移交，执行继续受依赖阻塞。 |
| todo、false、审查失败 | 保持 false，报告具体缺项和需要决定的事项。 |
| 已为 true 的 todo 或 in_progress | 只读复审，不重复写入同值；失败时保留实际许可并明确报告仍可能被调度或正在执行。撤销许可或停止执行需要另外明确授权及既有控制流程。 |
| in_progress、false | 报告运行中许可锁，不新启用，也不改状态绕过。 |
| done | 按 handoff 策略报告已完成、无需移交，不重开或更新许可；这是模式策略，不是 API 禁止。 |
| active 或 released worker | 保留所有权和原执行约束。released 即使为 todo，恢复仍需原 worktree/Agent 连续性确认，不能因启用许可而任意新建执行。 |

flag 更新不包含附件的原子保护。可变引用按实际内容核验，发生实质变化时重新审查
受影响部分；task version、附件清单与时间戳不能充当内容冻结。执行开始前仍须重新
读取任务和必要资料。handoff 不提供服务端审查证书或对后来内容的永久认证。

版本冲突后重新读取并判断，不仅更换版本重放。写入结果未知时先读取协调，读取失败
则保持未确认并保留真实错误；不自动重发。最终 GET 可能因调度器立即认领而显示更高
版本或 in_progress，应报告实际观察，不要求它与启用响应版本相等，不推断写入归因。

结果包括内容结论、必要修改或缺项、实际版本、flag、状态、依赖阻塞和 worker 约束。
许可为 true 不能证明执行开始或完成；实际观察到开始时应如实报告。handoff 本身不进入
当前会话的 run-task/autopilot，不修改状态、依赖或平台，不授予独立交付权限。
