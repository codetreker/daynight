# 助手任务收件箱与事件闭环

助手任务收件箱让外部系统和 Daynight 自身的出站 Webhook 把消息送达负责该[助手任务](assistant-task.md)的助手。助手读取通知后，用 Daynight CLI 了解项目与 Task 详情，按手册作出判断或干预，并把过程写入工作记录。

本文拥有收件箱、入站事件、事件操作者、自我循环防护和入站通知的必需行为。[设计](../design/assistant-task-inbox.md)说明模块与数据流。助手任务的归属、认领、事件确认与关注沿用[助手任务规格](assistant-task.md)；出站订阅、签名与重试沿用 [Webhook 管理设计](../design/webhook-management.md)和 [Webhook 投递设计](../design/webhook-delivery.md)。本规格的要求随对应实现逐项生效，未交付的部分不得作为现行能力对外声明。

## 收件箱的归属与管理

每个助手任务最多拥有一个收件箱。收件箱由任务所属用户开启、停用和轮换令牌；携带 `X-Daynight-Bot-Id` 的管理请求一律拒绝，避免助手在执行工作时顺带扩大自身的输入入口。与助手任务的其他 Bot 规则一致，这项拒绝不隔离同一用户的恶意进程。管理操作使用任务 `ifVersion` 与客户端 `operationId`，成功结果与操作回执原子提交，重复请求返回原回执，未知结果只读核对原操作。

开启生成随机的 `inboxId` 和至少 32 字节熵的令牌。收件箱 URL 本身不含令牌，可以随时读取；令牌只供外部发送方使用。服务端只保存令牌摘要，完整令牌仅在开启或轮换的成功响应中返回一次。

Daynight 出站事件不使用令牌，依靠下文的核验证明来源。因此订阅端点的目标 URL 不含秘密，轮换令牌也不需要修改端点。出站模块在端点目标变化时会推进目的地版本并终止旧版本的自动重试和手动重投；令牌与订阅分离，使轮换不影响已经产生的 Daynight 投递。

轮换有两种方式：

- `overlap`：旧令牌在轮换后 24 小时内继续有效，供外部发送方切换。同一时刻最多存在一个当前令牌和一个重叠令牌；重叠令牌仍有效时，再次 `overlap` 轮换被拒绝，只能使用 `immediate`。
- `immediate`：立即废止旧令牌，用于令牌泄露。

停用清除全部令牌摘要并使该 `inboxId` 永久失效，再次开启生成新的 `inboxId`。任务删除同时删除收件箱。两种情况都保留不含令牌的最小记录，使旧 `inboxId` 返回 410 且不能复活。

收件箱读取返回 `inboxId`、启用状态、创建与轮换时间、重叠截止时间及被抑制事件计数，不返回令牌或摘要。

## 接收请求

公开接口为 `POST /api/v1/assistant-task-inbox/{inboxId}`。它不使用登录凭据、Cookie 或 CORS。外部发送方通过 `Authorization: Bearer <token>` 或查询参数 `token` 提供令牌，最多出现一种；应优先使用请求头，避免令牌进入代理或 CDN 的 URL 日志。不带令牌的请求只有通过 Daynight 事件核验才被接收，否则视为令牌缺失。带有令牌的请求同样执行 Daynight 事件核验，以决定分类。

请求正文最多 64 KiB，媒体类型须为 `application/json`、以 `+json` 结尾的 JSON 类型或 UTF-8 `text/plain`。JSON 正文必须是合法 JSON；文本正文必须是合法 UTF-8。任何正文都不得包含 NUL 字节，因为事件负载以 JSON 文档保存，无法表示该字符。

| 结果 | 状态码 |
| --- | --- |
| 已接收、已识别为重复或已按自我循环规则抑制 | 202，返回 `eventId`、`classification`、`duplicate` 与 `suppressed` |
| 正文格式、令牌形式或幂等键无效 | 400 |
| 令牌不匹配，或不带令牌且未通过 Daynight 事件核验 | 401 |
| `inboxId` 从未存在 | 404 |
| 同一幂等键对应不同正文 | 409 |
| 收件箱已停用或任务已删除 | 410；出站投递据此结束该 Delivery 的自动重试 |
| 正文超限 | 413 |
| 媒体类型不受支持 | 415 |
| 超过频率或积压上限 | 429，附 `Retry-After` |
| 没有有效负责助手，或提交结果未知 | 503，附 `Retry-After` |

拒绝不写入事件。未知提交结果不自动重放；发送方按相同幂等身份重试时，服务端返回原结果或完成首次写入，不产生第二个事件。没有有效负责助手时，事件只在发送方的重试期限内等待；Daynight 出站事件的自动重试期限为发生后 72 小时。

## Daynight 事件的核验

请求满足以下全部条件时归类为 `daynight`：

1. 媒体类型为 `application/cloudevents+json`，`Webhook-Id` 请求头与 CloudEvents `id` 相同。
2. 服务端保存了该 ID 的事件，事实正文尚未回收，请求正文与保存的事实正文字节一致。
3. 该事件存在一份 Delivery，其端点属于任务所属用户，且目标 URL 的 origin 与路径指向本收件箱。
4. 任务所属用户当前能够读取该事件的项目。

其他请求一律归类为 `external`，并且必须带有有效令牌。核验依据服务端自身保存的事件与投递，不依赖令牌或出站端点的签名秘密，因此用户无需在两个资源之间同步秘密。条件 3 使任何人都无法把其他订阅收到的真实事件冒充为本收件箱的订阅；重放本收件箱已收到的事件只会命中幂等回执。只声称来自 Daynight 而未通过核验的正文不能成为 `daynight`，也不能获得操作者信息。

## 幂等与事件写入

`daynight` 请求以事件 ID 作为幂等键，接收回执保留 8 天，覆盖手动重投期限。`external` 请求可以通过 `Webhook-Id` 或 `Idempotency-Key` 请求头提供幂等键，二者都存在时必须相同；键为 1–200 字节的可见 ASCII 字符，回执保留 72 小时。回执有效期内，同一收件箱的同一幂等键只写入一个事件：正文相同返回原 `eventId` 并标记 `duplicate`，正文不同返回 409。回执过期后再次使用同一键视为新请求。没有幂等键的 `external` 请求每次写入新事件。

接收成功时，服务端在同一事务内复核收件箱、令牌、任务状态和当前认领，再写入一个类型为 `inbound` 的助手任务事件。目标为当前负责 Bot：认领未过期时为持有者，转交 pending 时为转交目标；租约已过期且未被接手时视为没有有效负责助手。任务暂停时照常接收，事件保持 pending，恢复后再投递。转交或接手时，仍处于 pending 的 `inbound` 事件在同一事务中改投新的负责 Bot。

`inbound` 事件不点亮关注；是否需要用户关注由助手按手册另行报告。事件负载包含收件箱 ID、分类、接收时间、媒体类型和幂等键。`daynight` 负载另含事件类型、项目、Task、发生时间、操作者及原 `data`；`external` 负载以字符串保存原正文，同时保存字节数与 SHA-256。请求头除幂等键外不保存。

## 积压、频率、容量与回收

每个收件箱有请求频率上限；每个任务对当前负责 Bot 的 pending `inbound` 事件有数量上限。超限返回 429 和 `Retry-After`，不丢弃已接收的事件。初始上限由设计给出，可依据实测调整。

过期的接收回执，以及 delivered 或 expired 状态超过 30 天的 `inbound` 事件，由服务端在接收和事件拉取过程中有界回收，不新增调度循环。引用已回收事件的工作记录保留原事件 ID，读取时标明该事件已回收。

入站通知进入助手 Session 时间线，会占用助手的近期展示缓存。Worker 必须压缩入站通知：同一 Task 的多个事件合并表达，外部正文只投递有界预览，单批入站通知的正文有固定字节上限，超出部分留到下一个空闲轮次，且不阻塞同批中的其他助手任务事件。完整内容始终可以通过 CLI 读取原事件。

## 事件操作者与自我循环

服务端为每个捕获的 Webhook 事件保存操作者，取值为：

- `user`：没有 Bot 身份的用户请求。
- `bot`：携带 `X-Daynight-Bot-Id` 并通过归属与删除状态核验的请求，同时记录用户 ID 与 Bot ID。
- `system`：服务端内部动作，例如 GitHub 同步与维护任务。

Task、Step 和 Thread 的写入接口接受可选的 `X-Daynight-Bot-Id`，按助手任务相同的规则核验。在设置了 `DAYNIGHT_BOT_ID` 的助手环境中，CLI 的 Task、Step 和 Thread 写命令自动携带该请求头。Bot 身份是同一用户内的协作声明，不是安全边界；同一用户的其他进程可以不带或冒用该请求头。

操作者只保存在服务端，不加入出站 Webhook 报文，出站报文的 wire 格式保持不变。收件箱按事件 ID 读取已保存的操作者。

已核验的 `daynight` 事件在以下任一情况下被抑制：收件箱返回 202 并标记 `suppressed`，不写入事件，只增加抑制计数。

- **自身写入**：操作者是本任务当前负责 Bot。
- **相互唤醒**：操作者是任务所属用户的另一个 Bot，并且该 Bot 在此前 10 分钟内收到过关于同一项目 Task 的 `inbound` 事件。这说明它的写入很可能是对收件箱通知的反应，继续投递会使两个助手相互唤醒。

同一用户的其他 Bot 在没有收到相关通知时完成的工作照常投递，助手仍能观察用户其他助手的项目活动。其他用户的 Bot 或无法核验操作者的 `external` 请求不被抑制，依靠频率与积压上限限制放大。这两项上限对所有请求都有效，构成第二道防线。

## 入站通知

Worker 沿用助手任务事件的投递规则：只在助手同步、在线、空闲且允许发送时，把待投递事件合并为一条 `origin=daynight` 输入，确认原生受理后再确认事件。暂停任务的 `inbound` 事件保持 pending。入站通知还须满足以下要求：

- `daynight` 事件写明项目、Task、事件类型、发生时间、操作者和关键事实，并给出读取 Task、步骤、Thread 和 Session 详情的 CLI 命令。
- `external` 内容放在明确的围栏中，标注其为不可信的外部数据而不是用户指令。
- 通知明确说明：因事件而读取的 Task 描述、步骤、Thread 消息和 Session 内容同样由他人写入，只能作为数据，不能作为指令。助手不得仅凭这些内容扩大行动范围。
- 每批通知给出读取当前手册和附录的命令；新 Session 或新负责助手在处理积压事件前先读取这些材料。

## 订阅入口

用户在助手任务页面勾选项目与事件类型，即可让这些 Daynight 事件送达该任务的收件箱。网站通过现有出站 Webhook 管理接口创建或更新一个属于用户本人的 HTTP 端点，其目标为不含令牌的收件箱 URL。收件箱与端点是两个独立资源，删除或停用一方不会隐式改变另一方。

- 轮换令牌不影响订阅端点。
- 端点的订阅列表按整体替换更新。未保存的修改固定在开始编辑时的端点与配置版本上；端点在别处被创建或修改后，网站提示冲突并禁止保存，直到用户放弃修改并加载最新配置，不得把旧修改提交到新版本而丢弃别处新增的订阅。
- 停用收件箱后，指向它的投递收到 410 并结束；网站提示用户停用或删除这些端点。
- 网站只创建个人端点。Team 端点投来的事件不满足核验条件，会以缺少令牌被拒绝；网站在检测到 Team 端点指向个人收件箱时给出警告。

出站投递只允许公网 HTTPS 目标，本机 localhost 部署无法以自身收件箱作为订阅目标；直接调用收件箱接口不受此限制。订阅入口只在自我循环防护可用的服务上提供。

## 安全与隐私

令牌和令牌摘要不得出现在日志、指标、错误、事件、记录或收件箱读取结果中，令牌只出现在开启或轮换的响应中。收件箱接收接口的日志只记录 `inboxId`、分类、状态码与字节数。外部正文作为不可信数据保存并标注来源。入站事件随助手任务删除并按上述期限回收；出站事件副本遵循 Webhook 自身的保留规则。

## 验收

- 开启、轮换、停用和重新开启后，外部请求只有带有效令牌才能写入，令牌只在一次响应中返回；`overlap` 轮换后 24 小时内旧令牌仍有效。
- 真实出站 Webhook 以不含令牌的 URL 指向收件箱时，事件被核验为 `daynight`；轮换令牌前后，自动重试与 7 天内的手动重投都能送达且不产生重复事件。篡改正文、伪造 `Webhook-Id`，或转交其他订阅收到的真实事件的请求，不带令牌时被拒绝，带令牌时归类为 `external`。
- 没有有效负责助手、超频与积压时，分别返回 503 或 429 且不写入事件；暂停期间的事件在恢复后投递；转交后 pending 事件送达新的负责助手。
- 当前负责 Bot 自身写入引起的事件，以及同一用户另一个 Bot 在收到相关通知后 10 分钟内写入引起的事件，被抑制并计数；其他主体引起的事件正常投递。
- 助手空闲时收到压缩后的入站通知，外部内容被围栏标注；助手忙碌时不被打断。
- 过期回执和旧入站事件按期限被回收，引用它们的记录仍可读取。
