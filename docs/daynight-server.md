# daynight-server 代码组织规则

## 文档职责

新增、修改或 review daynight-server 前，必须先阅读并遵守本文。

本文只记录稳定的代码组织规则。只有规则变化或新增时才修改本文；模块的新增、删除、重命名或移动本身不要求修改本文。

实际模块、目录结构和具体机制由源码及架构文档维护。本文不维护模块清单、完整目录树或迁移进度，也不作为项目实际结构的 source of truth。

## 分层职责

| 位置 | 职责 |
|---|---|
| `server` | HTTP 入口、路由、请求解析、响应编码、协议认证接入与 HTTP 生命周期 |
| `service` | 模块实例化、依赖组装、跨业务模块的流程集成，以及共享资源生命周期 |
| `core/<module>` | 模块自身的业务规则、权限判断、状态转换和业务操作 |
| `core/store` 根包 | DAO 接口、查询与写入参数、数据访问结果、事务与快照等接口合同 |
| DAO 实现子包 | 实现 store 接口，封装 SQL、数据库映射、驱动、连接、迁移和事务执行 |
| `utils/<purpose>` | 无业务语义、按用途明确命名的通用技术能力 |

按职责确定代码归属，再按领域组织模块。core 和 service 的目录不要求逐项对应，也不要求每个 core 方法都有一层 service 转发。

## 业务与集成

模块自己的业务规则和操作放在 core。跨模块业务流程由 service 协调，各模块仍负责执行自身规则。

server 调用组装好的模块或集成用例，负责 HTTP 协议适配，不承载跨模块业务编排，不执行 SQL。

HTTP 认证接入不替代业务模块内的权限检查。涉及多个模块的权限与状态判断，由 service 在相应一致性作用域内协调。

## DAO 接口与实现

DAO 接口统一定义在 core/store 根包，按领域分文件组织。接口使用数据访问所需的参数、结果和共享模型，不暴露数据库驱动类型。

core 业务模块只依赖所需的 DAO 接口，不依赖具体 DAO 实现，不直接操作连接池、执行 SQL 或进行数据库行扫描。

store 根包不依赖具体实现、数据库驱动或业务模块。具体实现依赖 store 接口；service 的组装入口负责创建实现并注入业务模块。

SQL、数据库字段映射、数据库锁的执行以及事务提交与回滚由 DAO 实现承担。业务状态转换和跨模块流程不放入 DAO。

## 模型与依赖

业务模块与 DAO 共用的数据模型应独立于业务操作、DAO 实现和 HTTP 入口。模型的具体包位置由模块设计确定，依赖关系必须保持无环。

core 不依赖 service 或 server。HTTP DTO 与传输格式的转换由协议适配承担；业务模型不以 HTTP DTO 作为公共模型。

领域错误应独立于 HTTP 状态码，错误到 HTTP 响应的映射由 server 负责。

业务准入与协议输出需要共用精确编码规则时，将数据类型和编解码放在共同依赖的纯协议包中，保持统一的格式与容量计算；该包不反向依赖 HTTP 入口或业务流程。

## 事务与一致性

事务与快照通过 store 中的接口合同表达，数据库驱动及事务执行细节留在实现中。

单模块操作可以在模块内部使用事务作用域；跨模块操作需要整体原子性时，由 service 协调相关模块使用绑定到同一事务的 DAO。参与该作用域的模块不得自行独立提交。

拆分模块或 DAO 时，必须保持既有的原子性、快照一致性、权限与版本检查、锁顺序以及失败语义。不同业务操作需要不同的锁定规则时，应保留各自的事务合同。

数据库事务不能自动覆盖文件、网络或连接等外部副作用。跨模块流程必须明确副作用的执行顺序、资源所有者和失败后的处理。

## 实例化与生命周期

service 负责共享依赖和模块实例的创建、连接及关闭关系。启动失败时清理已经创建的资源；关闭时先停止使用依赖的工作，再释放底层资源。

server 管理 HTTP listener、HTTP server 和请求的生命周期，并与模块关闭协调，避免资源释放后仍有业务操作访问它们。

具有业务含义的类型、校验和协议归对应业务模块或独立协议包。utils 不承载业务权限、业务状态或跨模块集成。

## 测试职责

业务规则与 service 编排的单元测试使用合成领域数据；需要查询结果、存储错误或事务完成结果时，通过 `core/store` 的 DAO、scope 与 transaction 接口 mock 控制并验证返回值、参数、调用和错误链。纯函数直接构造输入，不为使用 mock 引入存储依赖，也不为取得固定模型数据启动 PostgreSQL。

Mock 只实现当前规则需要的接口能力，未配置或额外调用应立即使测试失败。事务 callback、拟写参数与 committed、not_committed、unknown 结果必须分开；记录过写入不等于已经持久化。并发顺序只验证同一逻辑操作或明确 barrier 的关系，不要求所有 goroutine 使用全局 FIFO。后台未预期调用也必须独立标记测试失败并完成取消与 drain。不要 mock SQL 字符串或另建完整内存数据库来模拟 PostgreSQL。转换后的业务规则选择应能在未设置 `DAYNIGHT_TEST_DATABASE_URL` 时实际执行；不得以跳过测试或默认空结果代替隔离。

真实 SQL、约束、锁、事务提交与回滚、持久化读回以及跨操作的权限和版本重新检查由 PostgreSQL 集成测试证明。HTTP 与进程测试保留其装配和协议边界。拆分纯规则矩阵时，必须保留这些独有证明；一次函数调用不能替代真实事务或跨调用状态变化。

## 结构调整

调整模块位置或拆分职责时，同步相关测试、构建脚本、生成资源路径，以及记录具体结构和机制的架构文档。

模块和目录变化遵守本文规则；仅当规则本身发生变化或需要新增规则时修改本文。
