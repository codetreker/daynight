# Session 重连故障诊断与原会话恢复

状态：待实现。本文规定重连失败的诊断机制与恢复约束，不代表任何已有断连会话已恢复。

## 问题与目标

Web Session 的 Controller 可以完成身份握手、事件确认和状态同步，随后因服务端操作失败而断开。页面显示“执行环境连接中断”，但 Worker 仍能观察原 Controller。Worker 在线、Controller 存活和 Session 通道可用是三个独立事实。

当前服务端将 Controller 通道中不同阶段的失败统一记录为 `session/channel`。服务层可能把关联记录缺失转换为 `not_found: Session was not found.`，该错误不证明 Session 主记录不存在。Controller 的历史同步请求又只记录 HTTP 状态，因此连接失效引起的后续 `409` 容易被误认为最初原因。

目标是在不改变权限、执行身份和历史完整性规则的前提下，保留足以定位首次失败的信息，并以确定性证据约束恢复。诊断改进与具体断连根因修复必须分别验证；增加日志本身不构成会话恢复。

## 已有机制与证据边界

Controller 在收到身份匹配的 `welcome` 后进行 operation reconciliation、source events 确认和 `sync_state`。服务端同时轮询待投递操作与媒体请求。任何阶段失败均可能导致断连；随后发出的历史同步请求会因连接或 fence 失效被拒绝。

隔离 PostgreSQL 下的普通 `ContentRevision=2` 流程能够连续完成重连、空 reconciliation、heartbeat、state events、状态同步及轮询。这不足以证明线上状态健康，也不支持把所有新协议连接都视为故障。

冻结的历史同步 intent 保留原 ID、正文和摘要。旧 epoch 的部分上传可以被服务端结算为失败，客户端读取匹配回执后再生成当前 checkpoint。因此不得仅因 intent 的 epoch 较旧就删除它；结果未知的原提交仍需要按原身份查询。

具体线上断连尚缺能指向首次失败调用的证据。可选行缺失、悬空媒体请求、凭据状态等均须单独验证，不作为已确认根因。

## 服务端失败阶段

HTTP/WebSocket 适配层拥有协议阶段名称，业务层和存储层继续拥有原错误及其 cause。Controller 通道记录下列固定阶段：

|阶段|含义|
|---|---|
|`controller_connect`|hello 对应的连接准入或建立失败|
|`controller_source`|建立连接后读取确认序号失败|
|`controller_fence`|收到不属于当前连接的帧|
|`controller_handle`|处理已解码的 Controller 消息失败|
|`controller_poll`|周期轮询待投递内容失败|

`controller_handle` 额外记录受控枚举中的消息类型。不得将任意客户端字符串作为日志字段，也不记录消息正文、参数、图片、token 或原始数据库错误。

沿用现有 `httpx.LogFailure` 的错误分类、request ID 和脱敏规则。服务端日志额外保留存储错误的静态操作 phase，不能因包装为领域 `not_found` 丢掉这一定位信息。该字段只存在于服务端诊断日志，不加入公开错误响应。字段仅接受本通道实际调用的存储阶段白名单，并映射为固定标识符；不能仅靠字符过滤接纳任意错误文本，也不使用数据库驱动文本替代它。

公开 WS 错误仍保持现有 code/message 和 fence。错误后继续按现有规则关闭连接，不将 `not_found` 吞掉，不新增自动替代 Session 或重放输入。

## Controller 历史同步诊断

失败的 `GET status` 和 `PUT chunk` 分别记录固定操作名、HTTP 状态，以及响应中可安全提取的错误 code 和 request ID。错误 code 限制为 1–64 个小写 ASCII 字母、数字和下划线；request ID 沿用产品规则，限制为 1–128 个 ASCII 字母、数字、下划线或连字符。任意 message、响应正文、URL查询、其他 header 和凭据均不得进入日志。

读取失败响应最多 16 KiB，并受原请求的 15 秒 deadline 和调用方取消信号共同约束；超限或取消时取消剩余响应流。空响应、非JSON、超限、不可读或不符合格式时保留“HTTP失败”的原始事实，不用解析失败覆盖它。诊断不触发额外网络请求或重复提交。

保留 `status` 属性及既有 `404` 查询分支，使原 intent 的查询、匹配回执、失败结算和结果未知处理不受诊断修改影响。日志中的业务码只用于定位，不作为绕过原 receipt/fence 校验的授权。

## 具体根因修复的准入与范围

取得首次失败阶段后，应在拥有该机制的最小层次构造确定性回归，再修改实际错误路径。存储映射和并发问题使用隔离真实 PostgreSQL；协议编码、错误呈现及响应体限制使用对应适配层测试。人为 mock 一个 `not_found` 只能证明错误呈现，不能证明线上根因。

可恢复的附属请求应在其自身原 ID 下形成真实失败或拒绝结果；是否允许主 Session 继续连接，必须由被证明的业务条件决定。权限失效、旧 fence、无法确认原执行停止、未知提交结果以及真实历史缺口仍保持拒绝。不得添加全局“忽略 not_found/409”的恢复规则。

本设计不处理已经被标记不完整的历史归档、不解除任务暂停，也不修改 Worker 并发容量。

## 验证与完成条件

诊断实现应验证：

- 各 Controller 失败阶段及消息类型能准确区分，公共协议保持兼容。
- 包装后的存储错误仍有安全 phase；无存储错误时不伪造该字段。
- code/request ID合法、非法、超长、嵌套错误、非JSON、截断、超限及响应流失败均有测试；敏感 canary 不出现在日志。
- `404`查询后上传、完整/失败回执恢复、取消及结果未知仍按原身份工作，无额外提交。

断连根因修复另须证明原失败场景在旧实现中可复现、修复后消失，并覆盖相邻权限/身份拒绝条件。真实恢复验收保留同一 task、claim、Session 和 nativeSession，观察 source ACK 推进、多个心跳窗口连接稳定、CLI状态与历史读取以及实际页面一致。

本地测试、PR检查、发布版本、生产部署与原会话恢复分别记录。未部署或缺生产证据时不得声明线上问题已修复。

## 替代方案与代价

**重启或重建 Session。** 重启已经可能保留相同失败状态；重建会改变执行身份并增加重复输入和历史断裂风险，不用于掩盖未知根因。

**直接删除旧历史 intent。** 无法区分未提交、部分提交和丢失回执，会丢失恢复依据，因此继续使用原回执协议。

**打印完整错误与响应。** 能获得更多细节，但可能泄露凭据和用户内容；采用静态阶段与受限标识符，代价是仍需服务端内部证据来解释具体业务状态。

**统一放宽缺行或冲突检查。** 会把合法拒绝变成成功，无法保证权限和历史完整性。仅在确定性复现支持的具体分支处理恢复。
