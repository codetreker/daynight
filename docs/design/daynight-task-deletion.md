# Task 软删除设计

[需求](../spec/daynight-task-deletion.md)定义 CLI、Web 和 HTTP 的删除行为。任务仍使用三种业务状态，软删除是持久化可见性标记，避免把数据保留混入执行状态转换。

## 存储与事务

`017_task_soft_delete.sql` 为 `tasks` 增加可空 `deleted_at timestamptz`。新旧未删除记录均为 NULL；迁移保留原版本、业务时间、状态、属性及依赖。删除不调用任务元数据重写、依赖替换或附件删除逻辑。

删除复用现有项目行锁和事务内成员权限核对。读取目标后先验证精确版本，再拒绝 active worker 归属及任何未删除后继。所有写入均遵守项目锁，因此并发新增依赖与删除不能同时成功。允许没有 active 归属的人工进行中任务删除；release/completed 历史保留。

成功时在同一事务标记 `deleted_at`、更新 `updated_at`、递增任务版本并轮换 `projects.task_cache_epoch`。删除本身不改业务状态或执行时间，不物理删除任务、历史依赖、附件元数据或文件。事务失败优先暴露实际存储错误，不能将部分结果解释为删除成功。

## 可见性与引用

枚举、ready、TasksByID 前置查询、完整图、同步摘要、统计及可达性都基于 `deleted_at IS NULL`。依赖记录保留，但已删除源任务不参加活动图边数、环检测或后继保护。删除拒绝活动后继，因此活动图始终保留完整前置上下文；后续创建或修改依赖也不能引用已删除任务。

定点任务读取区分不存在与存在删除标记。服务先核对项目可见性，授权成员访问删除标记返回 `410 task_deleted`，不存在/错误项目/非成员返回 `404 not_found`。任务 GET、PATCH、状态、worker 和附件共用该判别，附件保留的字节不能绕过任务权限。DELETE 成功是无正文 `204`，重复删除为 `410`。

## 同步与缓存

窗口增量只返回当前任务，没有墓碑消息。每次删除在同事务轮换现有项目 epoch，旧 epoch 的下一次同步按[缓存设计](daynight-task-sync.md)返回完整 snapshot，原子替换摘要、详情及派生图。其他标签页无需理解新的同步字段，也不能继续以旧 generation 发布删除前内容。

这使删除承担一次项目完整同步的成本，并保持已有 DTO 与持久缓存结构。普通元数据、状态写入和重启继续保留 epoch；数据库恢复和历史替换仍遵循各自维护流程。

## CLI 与 Web 操作

CLI 的共享命令定义提供 `delete`、project 和精确版本选项。命令层按现有写操作规则处理显式版本与一次预读，API client 发送带 JSON 版本的 DELETE 并要求 `204`，不解析 Task 正文。错误沿现有链路传递，网络失败保留未知结果语义，不重试。

`TaskDetailSurface` 在共享标题栏提供删除操作，并复用 `TaskConfirmation` 的 alertdialog、取消初始焦点、Escape、Tab、遮罩和 inert 生命周期。确认绑定当前任务及业务版本；任务切换或新观察使旧确认失效。删除文案和危险操作样式在两种详情容器及两种语言保持一致。

`TaskDetailSessions` 是删除与既有三类写入的共同所有者，提交后保留操作身份与未知结果核对。可信 `task_deleted` 是任务局部终态：清除任务正文、禁用写入并请求项目同步，不能进入 `not_found` 的项目撤权分支。已提交操作的身份检查、释放后处理及 generation fence 继续生效。

成功删除、重复删除或 GET 核对得到 `410 task_deleted` 后，弹窗由图中任务消失的既有规则关闭并恢复有效焦点；独立页显示终态和返回项目入口。GET 若显示任务仍存在，保留已核对结果及现有任务资料，不自动再次提交。核对失败保留可见错误与显式只读重试。
