# Task 软删除设计

[需求](../spec/daynight-task-deletion.md)定义 CLI、Web 和 HTTP 的删除行为。任务使用proposed、todo、in_progress、done、cancelled五种业务状态，软删除是持久化可见性标记，避免把数据保留混入执行状态转换。

## 存储与事务

`017_task_soft_delete.sql` 为 `tasks` 增加可空 `deleted_at timestamptz`。新旧未删除记录均为 NULL；迁移保留原版本、业务时间、状态、属性及依赖。严格删除保留全部边；显式解除引用复用同一事务删除传入边并更新源任务版本，不重写其他依赖或附件。该选项不改变存储格式或新增迁移。

删除复用现有项目行锁和事务内成员权限核对。Scoped 删除先通过不获取 Task 行锁的可见性读取执行目标授权；Goal 保留 Project → Team 图锁 → Task 的既有顺序。首次获取 Task 行锁前，枚举目标、仍可见后代和显式解除引用的全部源行，按 UUID 升序取得最终锁模式，再读取目标并验证精确版本和 active worker 归属。removeDepends 省略/false 时继续检查所有未删除引用者，有引用者则拒绝；true 则生成解除全部传入引用的删除计划。准备回调只校验并保存计划，不能执行 SQL 修改：领域 Fault 由外层事务正常结束后返回，准备中写入会把拒绝错误地提交。

真实解除引用位于删除执行路径，通过项目锁下当前入边选择全部源任务，包括已删除源任务；删除这些源指向目标的普通/外部边，并按源任务去重后各递增一次 version 与更新 updatedAt，再标记目标。源任务的其他边、assignedTo、状态、计时、worker claim 与删除标记保持不变，源 active worker 不构成限制；目标自己的所有出边保留。任何一步 SQL 或事务失败回滚全部修改。

所有写入遵守项目锁。新增引用先提交后，带 true 的删除可以继续成功并清除该引用；删除先提交时新增引用查不到活动目标而拒绝。严格删除仍在新增引用先提交时拒绝。允许没有 active 归属的人工进行中目标删除；release/completed 历史保留。

成功时在同一事务标记目标 `deleted_at`、更新 `updated_at`、递增目标版本一次，保持 `projects.task_cache_epoch`。同项目后代沿 `parent_id` 遍历，遇到已物理或继承隐藏的节点即剪枝，仍可见后代写入与目标墓碑相同的 `ancestor_deleted_at`。仅隐藏不修改后代版本、业务时间、状态、归属、依赖、历史或事件；后代若也是解除引用的源任务，沿用一次实际解除引用的版本和时间更新。显式解除引用所需的源任务版本更新与入边移除也属于该事务。目标 assignedTo、业务状态、执行时间、数据库行、附件元数据和文件保留；严格模式保留历史入边，解除模式删除全部入边并保留目标出边。事务失败优先暴露实际存储错误，不能将部分结果解释为删除成功。

## 可见性与引用

本文以 `task_id → depends_on_task_id` 表示引用方向：传入边是其他源任务的 dependsOn 包含目标，目标出边是目标自己的前置。图上表达执行顺序的箭头方向仍遵守既有图协议。

对外枚举、完整图、同步摘要和统计使用有效删除事实：目标自身或任意祖先删除时资源不可见。`tasks.ancestor_deleted_at timestamptz NULL` 保存首次继承隐藏时间，`task_resource_rows.effective_deleted_at = COALESCE(t.deleted_at, t.ancestor_deleted_at)`，自身墓碑优先。视图保留原列名、顺序及类型，直属 Parent 的类型与物理删除字段保持原语义，内部标记不出现在公开 DTO。依赖准入、满足性、重开保护和环检测继续读取保留的物理普通 Task 与边，不将被父删除隐藏的前置当作不存在；新增依赖目标必须可见。已删除源任务不参加活动图边数、环检测或严格删除的引用保护，但显式解除模式仍移除它们指向目标的历史入边。严格删除保护未删除引用者，解除模式原子删除相应关系，两种路径都保持活动图前置完整。移除前置后 ready 与链分类按完整新快照重新派生，不级联更改任务状态或建立传递捷径。

定点任务读取区分不存在与有效删除。服务先核对项目可见性，授权成员访问有效删除资源返回指向请求目标的 `410 task_deleted`，不存在/错误项目/非成员返回 `404 not_found`。任务 GET、PATCH、状态、worker 和附件共用该判别，附件保留的字节不能绕过任务权限。[附件变更事务](daynight-task-attachments.md#postgresql-元数据)通过目标物理行锁与删除传播串行，删除提交后等待中的附件变更不执行文件操作。Session 普通访问同样不可用，原 owner 的停止和归档收尾保留既有例外。DELETE 成功是无正文 `204`，重复删除为 `410`。

## 迁移与恢复

迁移 123 在实际前一账本 122 后增加继承标记。迁移事务先验证历史数据仍符合同项目、Goal 为根且只有 Goal 直属普通成员的结构，再回填已删除 Goal 尚未物理删除的直属孩子，最后替换视图。异常记录以 Task、Project 和 Parent ID 定位，DDL、回填和账本一起回滚。空库使用匹配的 `schema/current.sql`，升级和快照须保持目录与初始数据等价。

部署先排空旧服务的请求、Worker 写入与 Webhook 后台投递，保存配对数据库和附件快照，再执行候选迁移。迁移提交后启动失败，须从新连接核对账本版本、checksum 和 schema。优先使用与当前账本匹配的修复制品；旧制品不能在新账本继续运行。若必须恢复旧制品，先核对迁移后的业务写入和外部效果，再按配对快照恢复，重新开放前轮换所有项目 task cache epoch。入口无流量不证明后台没有投递；已发出的 Webhook 等外部效果须单独记录与对账，数据库回退不会撤销它们。具体持久化操作遵循[配套恢复流程](../../deployment/localhost/README.md#persistence-and-backup)。

## 同步与缓存

[缓存设计](daynight-task-sync.md)的同历史增量返回有效删除 ID，包括继承隐藏的后代，并与存活摘要、依赖状态和覆盖水位原子应用。共享持久删除记录及读取资格检查阻止其他标签页的旧响应恢复已删除内容。

普通删除、元数据、状态写入和重启保留 epoch；数据库恢复和历史替换遵循[配套恢复流程](../../deployment/localhost/README.md#persistence-and-backup)，在重新开放服务前轮换 epoch。恢复删除前的历史可能重新出现相同 ID、版本和时间的活动任务；新 epoch 对应的 cacheGeneration 是重新读取该历史的边界。

## CLI 与 Web 操作

CLI 的共享命令定义提供 `delete`、可选 `--remove-depends`、`--force`、project 和精确版本选项。命令层预读目标类型和身份，显式版本保持原值；Goal 删除提示不可见范围、保留归属与后续观察停止，并要求交互确认或 force；不传开关保持严格模式，传入时明确携带 removeDepends=true。API client 发送带 JSON 版本和可选严格布尔 removeDepends 的 DELETE 并要求 `204`，不解析 Task 正文。错误沿现有链路传递，网络失败保留未知结果语义，不重试。

`TaskDetailSurface` 在共享标题栏提供删除操作，并复用 `TaskConfirmation` 的 alertdialog、取消初始焦点、Escape、Tab、遮罩和 inert 生命周期。确认绑定当前任务、业务版本、明确的 removeDepends=true 组合意图和已准入的 cacheGeneration；任务切换、历史替换或实质新观察使旧确认失效。文案解释清除执行时所有其他任务对目标的普通/外部引用，并提示可能改变 ready，不以当时数量限定授权。会话捕获该 true 意图并传入 API，传输层不推断删除模式；删除文案和危险操作样式在两种详情容器及两种语言保持一致。

操作接受时同步捕获审阅历史与 mutation 所有者，不能在异步准备后改用新 ticket 作为旧决定的权限。状态、许可、平台和删除均在每次异步准备完成后及请求发送前重新检查所有者、审阅 generation 与当前准入。`beginSync` 若返回替换历史的 ticket，即使相同 task ID/version 仍存在，也不能继续派发旧确认；该准备以零写入结束，只读刷新当前历史，fresh GET 后须由用户重新确认。已被较新操作取代的准备不能修改新 owner 的阶段或共享写锁。仅详情容器关闭不撤销仍属于原历史和 owner 的已接受意图。

提交准备与普通结果处理共用遵守身份 gate 的同步准入/副作用边界。同用户核验暂停时通过现有 `scope.ready` 等待，返回后重新检查身份生命周期、原审阅历史和当前 owner，再访问受保护的实时 getter 或修改阶段；等待后再次暂停时重新等待，不能在 catch 中继续调用同一受阻 getter。身份结束丢弃旧操作。未派发的过期准备结束为本地冲突或拒绝并 GET 当前历史；已经派发的旧历史结果保留 unknown 与只读核对语义，被较新 owner 取代的结果不修改 entry。

`TaskDetailSessions` 是删除与其他 Task 写入的共同所有者，提交后保留操作身份与未知结果核对。`TaskCacheScope.reportTaskDeleted` 接纳绑定原 opening 或原操作票据的可信 `204`、`410 task_deleted`；原身份、项目、资源、历史及当前所有者须仍匹配。它通过 `TaskReadAdmission` 为已确认目标与待核对读取推进局部资格修订，发出 `taskDeletionHint`，并共享提示之后启动的后台 TaskSync。普通 Task 的不可变祖先链可排除已证实无关条目；Goal 成员归属可变化，缺乏足够拓扑证据的活动详情必须重新读取。提示不写入 `taskRemovals`、不推进覆盖、不退休项目历史。完整图与业务依赖状态继续来自上一次权威提交；新 TaskSync 将实际删除集合、存活摘要和依赖状态原子发布后，按精确 ID 撤回详情、关系、附件、Session、搜索、My Tasks 和跨项目 Goal 上下文。无关读取及有效交互保持。真实 epoch 更替继续使用原项目历史围栏。

状态、许可、平台和删除的结果处理共用操作所有者与历史准入检查；成功、拒绝、冲突、未知结果及核对更新都不能跳过该检查。已提交操作的身份核对、释放后处理与项目撤权仍使用既有 scope/ticket 规则。可信同用户已提交 `404 not_found` 优先于普通结果的身份暂停等待，先经 `canRevokeProject(ticket)` 同步撤回匹配历史的准入与正文，再等待持久清理；不能因正向准入等待而延迟负向撤权，也不能撤回替换历史。目标删除本身不撤销项目成员权限。身份暂停保留已确认回执，恢复后重新检查原 owner、历史和票据，再接纳目标提示；原历史迟到 `204`、`410` 不撤回恢复后的同 ID 资源或其他新历史内容。未知写结果继续只 GET 核对，不因删除提示产生写重放。共享写锁只能由其当前 owner 的适用结果推进。删除终态绑定确认历史；获准新历史确证同 ID 仍可见后强制 live GET，成功前禁写。

成功删除、重复删除或 GET 核对得到当前历史的可信 `410 task_deleted` 后，目标详情及其资料立即退出，独立页显示终态和返回项目入口。待核对后代不作为有效详情或写入基线；新读取可重新确认存活资源，失败保留错误与只读重试。项目图等完整业务投影在权威提交前保留，提交后只移除实际删除目标与关联边，不能仅凭本地旧 Parent 集合发布半份图。删除最后成员保留同 Goal 宿主与空态，Goal 本身删除关闭对应图；正常同历史更新保持有效画布与视口，机制由[任务浏览设计](daynight-task-inspection.md#goal-整体图)拥有。
