# Task 软删除设计

[需求](../spec/daynight-task-deletion.md)定义 CLI、Web 和 HTTP 的删除行为。任务仍使用三种业务状态，软删除是持久化可见性标记，避免把数据保留混入执行状态转换。

## 存储与事务

`017_task_soft_delete.sql` 为 `tasks` 增加可空 `deleted_at timestamptz`。新旧未删除记录均为 NULL；迁移保留原版本、业务时间、状态、属性及依赖。严格删除保留全部边；显式解除引用复用同一事务删除传入边并更新源任务版本，不重写其他依赖或附件。该选项不改变存储格式或新增迁移。

删除复用现有项目行锁和事务内成员权限核对。读取目标后先验证目标精确版本并拒绝其 active worker 归属。removeDepends 省略/false 时继续检查所有未删除引用者，有引用者则拒绝；true 则生成解除全部传入引用的删除计划。准备回调只校验并保存计划，不能执行 SQL 修改：领域 Fault 由外层事务正常结束后返回，准备中写入会把拒绝错误地提交。

真实解除引用位于删除执行路径，通过项目锁下当前入边选择全部源任务，包括已删除源任务；删除这些源指向目标的普通/外部边，并按源任务去重后各递增一次 version 与更新 updatedAt，再标记目标。源任务的其他边、状态、计时、worker claim 与删除标记保持不变，源 active worker 不构成限制；目标自己的所有出边保留。任何一步 SQL 或事务失败回滚全部修改。

所有写入遵守项目锁。新增引用先提交后，带 true 的删除可以继续成功并清除该引用；删除先提交时新增引用查不到活动目标而拒绝。严格删除仍在新增引用先提交时拒绝。允许没有 active 归属的人工进行中目标删除；release/completed 历史保留。

成功时在同一事务标记目标 `deleted_at`、更新 `updated_at`、递增目标版本一次并轮换 `projects.task_cache_epoch` 一次。显式解除引用所需的源任务版本更新与入边移除也属于该事务。目标业务状态、执行时间、数据库行、附件元数据和文件保留；严格模式保留历史入边，解除模式删除全部入边并保留目标出边。事务失败优先暴露实际存储错误，不能将部分结果解释为删除成功。

## 可见性与引用

本文以 `task_id → depends_on_task_id` 表示引用方向：传入边是其他源任务的 dependsOn 包含目标，目标出边是目标自己的前置。图上表达执行顺序的箭头方向仍遵守既有图协议。

枚举、ready、TasksByID 前置查询、完整图、同步摘要、统计及可达性都基于 `deleted_at IS NULL`。已删除源任务不参加活动图边数、环检测或严格删除的引用保护，但显式解除模式仍移除它们指向目标的历史入边。严格删除保护未删除引用者，解除模式原子删除相应关系，两种路径都保持活动图前置完整。后续创建或修改依赖不能引用已删除目标；移除前置后 ready 与链分类按完整新快照重新派生，不级联更改任务状态或建立传递捷径。

定点任务读取区分不存在与存在删除标记。服务先核对项目可见性，授权成员访问删除标记返回 `410 task_deleted`，不存在/错误项目/非成员返回 `404 not_found`。任务 GET、PATCH、状态、worker 和附件共用该判别，附件保留的字节不能绕过任务权限。DELETE 成功是无正文 `204`，重复删除为 `410`。

## 同步与缓存

窗口增量只返回当前任务，没有墓碑消息。每次删除在同事务轮换现有项目 epoch，旧 epoch 的下一次同步按[缓存设计](daynight-task-sync.md)返回完整 snapshot，原子替换摘要、详情及派生图。其他标签页无需理解新的同步字段，也不能继续以旧 generation 发布删除前内容。

这使删除承担一次项目完整同步的成本，并保持已有 DTO 与持久缓存结构。普通元数据、状态写入和重启继续保留 epoch；数据库恢复和历史替换遵循[配套恢复流程](../../deployment/localhost/README.md#persistence-and-backup)，在重新开放服务前轮换 epoch。恢复删除前的历史可能重新出现相同 ID、版本和时间的活动任务；新 epoch 对应的 cacheGeneration 是重新读取该历史的边界。

## CLI 与 Web 操作

CLI 的共享命令定义提供 `delete`、可选 `--remove-depends`、project 和精确版本选项。命令层按现有写操作规则处理显式版本与一次预读；不传开关保持严格模式，传入时明确携带 removeDepends=true。API client 发送带 JSON 版本和可选严格布尔 removeDepends 的 DELETE 并要求 `204`，不解析 Task 正文。错误沿现有链路传递，网络失败保留未知结果语义，不重试。

`TaskDetailSurface` 在共享标题栏提供删除操作，并复用 `TaskConfirmation` 的 alertdialog、取消初始焦点、Escape、Tab、遮罩和 inert 生命周期。确认绑定当前任务、业务版本、明确的 removeDepends=true 组合意图和已准入的 cacheGeneration；任务切换、历史替换或实质新观察使旧确认失效。文案解释清除执行时所有其他任务对目标的普通/外部引用，并提示可能改变 ready，不以当时数量限定授权。会话捕获该 true 意图并传入 API，传输层不推断删除模式；删除文案和危险操作样式在两种详情容器及两种语言保持一致。

操作接受时同步捕获审阅历史与 mutation 所有者，不能在异步准备后改用新 ticket 作为旧决定的权限。状态、许可、平台和删除均在每次异步准备完成后及请求发送前重新检查所有者、审阅 generation 与当前准入。`beginSync` 若返回替换历史的 ticket，即使相同 task ID/version 仍存在，也不能继续派发旧确认；该准备以零写入结束，只读刷新当前历史，fresh GET 后须由用户重新确认。已被较新操作取代的准备不能修改新 owner 的阶段或共享写锁。仅详情容器关闭不撤销仍属于原历史和 owner 的已接受意图。

提交准备与普通结果处理共用遵守身份 gate 的同步准入/副作用边界。同用户核验暂停时通过现有 `scope.ready` 等待，返回后重新检查身份生命周期、原审阅历史和当前 owner，再访问受保护的实时 getter 或修改阶段；等待后再次暂停时重新等待，不能在 catch 中继续调用同一受阻 getter。身份结束丢弃旧操作。未派发的过期准备结束为本地冲突或拒绝并 GET 当前历史；已经派发的旧历史结果保留 unknown 与只读核对语义，被较新 owner 取代的结果不修改 entry。

`TaskDetailSessions` 是删除与既有三类写入的共同所有者，提交后保留操作身份与未知结果核对。可信 `task_deleted` 是当前项目历史中的任务局部终态：清除任务正文、禁用写入并请求项目同步，不能进入 `not_found` 的项目撤权分支。终态记录确认删除时的 cacheGeneration；后续已获授权的新 generation 完整快照同时包含该任务的活动节点和摘要时，清除旧历史的删除阻止并强制 live GET，成功前保持禁写。仅 generation 变化或旧缓存中存在相同 ID 都不足以重新准入。

状态、许可、平台和删除的结果处理共用操作所有者与历史准入检查；成功、拒绝、冲突、未知结果及核对更新都不能跳过该检查。已提交操作的身份核对、释放后处理与项目撤权仍使用既有 scope/ticket 规则。可信同用户已提交 `404 not_found` 优先于普通结果的身份暂停等待，先经 `canRevokeProject(ticket)` 同步撤回匹配历史的准入与正文，再等待持久清理；不能因正向准入等待而延迟负向撤权，也不能撤回替换历史。旧历史响应只能归属于原操作，不能清除恢复后的活动任务正文、重新设置删除终态、覆盖较新 mutation 的反馈或把其 pending/核对阶段改为空闲。较新操作持有的共享写锁只能由该操作的当前历史结果推进；旧操作的远端结果不授予它修改新历史视图的权限，也不产生新的写请求。

成功删除、重复删除或 GET 核对得到 `410 task_deleted` 后，弹窗由图中任务消失的既有规则关闭并恢复有效焦点；独立页显示终态和返回项目入口。GET 若显示任务仍存在，保留已核对结果及现有任务资料，不自动再次提交。核对失败保留可见错误与显式只读重试。

## 决策与验证
