# API 输入与资源计量设计

## 职责

[候选限额规范](../spec/daynight-api-input-limits.md)定义单位和数值。各 core 领域拥有自己的常量和纯候选检查；`internal/core/model/taskproperty` 保留结构 `NormalizeValue`，独立准入检查每个规范化值。普通资源读取直接消费写入入口生成的规范存储数据，不重复候选结构、字段或容量检查；正常解码和输出错误仍会传播。可分页资源按条数分页，完整目录保持原范围；读取不引入字节计量、历史兼容、扫描或迁移，也不将撤销的读取预算转为新写入配额。共享 MCP 入口仅对写入执行输出 schema 和容量准入，输入、并发、期限及 I/O 请求范围规则继续由各自合同拥有。Task 和 Step 共用文字策略，原有集合 codec 继续拥有 Steps 与 Thread 的编码额度。

`internal/core/inputpolicy` 以版本和稳定标识列出候选领域限额，供消费者识别规则。类型化容量失败携带字段、实际值、上限和单位，不保存输入。预算编码在首个超额字节停止时，报告已观察下界并明确标识，不能将它当作完整编码长度。结构错误及原有权限判断仍由各自所有者处理。

协议投影与编码需要由准入计量和实际输出共享，避免 JSON 转义、外壳、版本表示或换行产生偏差。预算写入必须在超限时明确失败；属性只计规范化 JSON 值。协议层不依赖 HTTP handler 或数据库。上游规范化 Profile 包含 identity ID 和落库字段；`/me` 响应使用本地 User ID 和 personalTeam，采用独立投影和含换行的计量，不能混用两者的外壳。

## 启用边界

纯业务策略不直接执行在线读写、文件 I/O 或数据库事务。Task 写入所有者在规范化后调用相应策略，并在事务提交前检查成功响应编码。MCP 计入对应 JSON-RPC ID、协议版本及实际 full/summary 投影；旧版批量请求在 SDK 分派前为 Task 写调用建立私有的逐项 ID 对应，并在工具处理前移除内部标记。原始 body 仍先受 4 MiB 限额。领域入口负责一致接入其准入规则，不能静默改写存量内容；不设离线扫描或统一启用门槛。传输额度的实施与错误语义见[服务设计](daynight-server.md)。完整目录未新增分页，其物化和历史增长风险保留；最终输出额度不构成全服务峰值内存保证。
