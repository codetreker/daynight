# 本地文件存储离线迁移

## 输入与停写边界

`daynight-server migrate-storage --root <配置根目录> --source-storage-root <原本地卷绝对路径>`
把同一停写点的本地文件与 PostgreSQL 数据迁入 Azure。配置沿普通服务的数据库与存储字段加载，
`database.url` 指向从原备份恢复的隔离目标库，`storage.backend` 必须显式选择
`azure-blob`。`storage.root` 是目标运行时的 scratch 目录，必须与原本地卷分离。
Managed Identity 与 Azurite 采用普通服务相同的配置和地址映射。

管理员先停止入口、排空应用与维护执行器，再取得 PostgreSQL 和本地卷的配对备份。
原始备份保持不变；命令读取原卷，只修改隔离目标库与目标容器。
目标库必须与候选代码的完整迁移账本匹配，命令不执行 schema migration、不启动 HTTP 服务或后台清扫。
所有直接数据库、文件和 Azure 写入者也必须保持停止，直到命令成功并完成切换。
数据库事务及对象条件创建不能替代这个停写条件。

## 保留对象与状态转换

附件清单包括数据库仍保留的所有 Task 和 Goal 附件，包含软删除所有者。
本地路径沿现有附件地址派生，Azure key 复用运行时映射；原始业务路径、长度、MIME、时间和权限保持不变。
附件没有持久摘要，命令核对数据库长度并计算源 SHA-256，然后才能写入目标。

Session 保留范围复用配对备份核验器：正式归档、媒体闭包、仍须保留的发布对象与旧归档转换记录。
退休完成文件及已经进入账本的 history 可能只需要回执，不重新要求已被正常回收的暂存字节。
迁移用撤销后的库存投影核验源和目标，因此确认未完成的归档与图片暂存不作为待复制正式对象。

确认未完成的归档文件必须没有可观察的正式发布对象。若正式对象存在，输出可定位的发布差异，
保留原登记和事实，等待修复或核对；命令不把发现的字节自动解释为完整业务回执。
完成、失败及未知结果记录均保持各自语义。允许撤销的 receiving 登记和对应旧分块在目标库事务中删除，
只有当前 `history_id` 或 `timeline_id` 指向该文件时才清空。
bundle 的准备阶段、revision、账本以及同批完成结果保持不变。替换 history 被撤销后，
账本仍可引用此前完成的 history；首次上传沿用原冻结身份和 revision。
授权状态查询返回普通未登记 `404`，v2 Controller 可以用原 `fileId` 从偏移 `0` 首次上传。
若被撤销文件是 `staging_corrupt` 终态的 successor，迁移在失败前件内部保存与完整原身份匹配的撤销事实，
公开错误与 `successorFileId` 回执保持不变。核验器仅在存在有效撤销证明时接受暂未登记的 successor，
已有 successor 仍执行完整身份与状态核验。重跑读取同一持久事实。
Controller 在本地已保存 replacement intent 且旧终态回执确认相同 successor 时转入该文件，
即使查询返回 `404`，也沿正常首次上传流程提交原冻结内容；缺少或不匹配的原始 intent 继续拒绝。
该恢复分支属于配套 Controller 候选，组合验收须固定使用包含它的提交。

未完成图片沿 release 语义保留身份、已确认偏移和 `released` 回执。
目标私有命名空间确认清理后才标记存储释放。MCP 旧票据沿普通清理与关闭规则结算目标私有对象和容量，
保留提交回执、操作记录及清理来源，结果未知的操作仍可按原身份查询。
源配对卷中的私有内容保持不变，供恢复原时间点使用。

## 复制、核验与失败

源对象先核对长度和已有摘要，随后通过 Azure 条件创建发布。
目标已经存在且长度、SHA-256 一致时可采用；不同字节是冲突，不覆盖。
复制结果未知时观察原目标，核验通过才能采用，不盲目重复写入。
目标读回与 Session 引用闭包通过后，才提交在途状态转换；之后再次核验目标数据库库存。
对象存储与数据库不属于同一个原子事务，失败可能留下已复制对象或已提交的状态结果，均须保留并观察。
重跑继续核对同一隔离目标和原始配对卷。

输出以运行 ID 关联对象清单、摘要、长度、状态处置和差异。
缺源、源数据不符、读取失败、复制失败、目标冲突和发布事实未能分类分别报告。
路径和业务 ID 用于定位，连接字符串、凭据及对象正文不进入诊断。
只有整轮退出状态 `0` 表示目标核验通过；任何早先的对象成功记录都不能替代最终成功。
存在差异或未完成核验时保持停写并修复隔离目标。

## 启用与恢复

核验成功后使用该目标库与 Azure 配置启动单实例服务，检查迁移对象读取、重新上传及受控重启。
恢复切换前时间点时停止服务，恢复未经修改的原 PostgreSQL 和本地卷，切回 `local`，
按[配对恢复流程](../../deployment/localhost/README.md#persistence-and-backup)轮换受影响项目的
`task_cache_epoch` 后再开放服务。恢复点之后的数据和外部效果需单独处理。
Azure 已开始接受写入后的配对备份、自动回退与跨主机部署具有各自范围。

## 验证职责

DAO 测试验证库存完整性、事务状态重核对、仅撤销匹配指针及 revision/账本/回执保留。
服务测试用真实 PostgreSQL 与隔离 Azurite 验证复制、读回、重跑、缺项、不符、冲突和失败保持状态。
真实 HTTP 路由验证撤销后未登记查询与从 `0` 首次上传；独立组合验收使用固定 Server 与 v2 Controller 候选。
切换前恢复验证必须读取原配对材料，不能借用已迁移目标掩盖缺失对象。
