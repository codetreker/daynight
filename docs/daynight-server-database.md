# daynight-server 数据库使用规范

本文规定 daynight-server 使用 PostgreSQL 时的业务、存储和并发控制职责。现有 SQL、约束和索引由各自的设计文档描述；既有机制的存在不构成新增同类机制的理由，调整时必须保留其对外保证。

## 业务规则与数据访问

业务规则由 Go 代码拥有。状态转换、权限决策、调度与重试策略、期限计算、业务数据合并、协议与 JSON 校验、正文哈希等，放在对应 core 模块或其共用的纯模型、协议包中。跨模块组合由 service 协调。

DAO 接收含义明确的查询或写入参数，执行数据访问并返回实际结果。不得在 SQL、数据库约束、trigger 或存储过程中另建业务状态机、策略计算器或协议解码器，也不得把业务拒绝主要交给数据库约束报错实现。

按规则的含义判断归属，不按 SQL 的长度或语法判断。`CASE`、CTE、`EXISTS`、递归查询本身不构成违规；需要关注它们是在完成数据查询，还是在决定业务行为。

| 场景 | 规则归属与数据库职责 |
|---|---|
| 任务进入执行、完成或取消状态 | core 决定哪些时间字段替换、保留或清空；DAO 提供所需的权威时间并原子保存结果 |
| Worker 本次上报不可用 | core 根据旧事实和本次报告决定保留、替换或标记 stale；DAO 通过原子预期条件校验或必要的互斥保护写入 |
| Webhook 重试计划、保留期限、事件正文 | 业务或协议代码生成并校验计划、字段组合与哈希；DAO 保存明确结果 |
| 列表过滤、排序与分页 | 领域模块定义筛选和排序语义；DAO 在分页前执行必要的 SQL 过滤与排序 |

SQL 可以承担投影、过滤、关联、排序、分页、聚合和批量读写。查询所需的权限过滤、依赖判定等集合条件，应遵循业务模块定义的合同，不能在 DAO 中形成可独立变化的另一套业务策略。必须在 SQL 执行的表达式，由规则层测试与 Store 测试分别证明决策和实际查询结果一致。

将规则移回代码时，必须保留查询的容量和分页语义。不得用全量取回后过滤或排序、内存分页或逐行补查，替代原有的有界集合查询。

## 数据库约束

数据库约束按承担的保证选择，默认采用以下边界：

| 机制 | 使用规则 |
|---|---|
| `PRIMARY KEY` | 标识记录并保证身份唯一 |
| `NOT NULL` | 用于存储模型中确实不可缺失的字段；可空性按字段语义确定 |
| `UNIQUE`、唯一索引 | 用于必要的并发唯一性、身份或幂等保证，明确唯一范围及 NULL 语义 |
| `CHECK` | 默认不承载业务枚举、取值范围、状态组合、协议或 JSON 结构、重试计划、期限、正文长度或哈希等业务校验 |
| Foreign key、级联更新或删除 | 默认不引入；确有必要时，说明保证、锁定和写入成本，并经用户确认 |
| Trigger、存储函数或存储过程 | 默认不用于执行业务校验、状态转换、策略计算或跨表业务编排 |

每项约束必须有明确用途。不得仅因“数据库还能再检查一次”重复业务代码中的校验。需要超出默认边界时，必须说明代码为何不能承担该保证、涉及哪些写入入口、数据库执行的成本，以及是否影响并发与失败语义。

主键和必要的唯一约束承担并发保证，不能用没有并发保护的“先查询是否存在，再插入”替代。仅把这两个操作放入普通事务，也不自动保证唯一性。

移除既有约束前，必须先核对它保护的全部写入入口和调用者可见行为。业务校验移到所有入口共享的规则所有者；跨行关系、唯一性或删除顺序等保证，还必须由正确的锁、条件写入或其他明确的原子机制承担。字段和 schema 的变更通过迁移完成，并由真实 Store 测试证明成功、拒绝及并发行为。

## 并发控制与锁

并发写入优先使用乐观锁：业务代码确定预期条件和修改内容，DAO 在实际写入时原子校验条件并应用修改。预期条件可以是版本号、当前状态、相关字段值或它们的组合，不要求统一使用版本号，也不要求为了乐观锁先读取一次记录。仅在代码中检查条件，再执行无条件写入，不构成乐观锁；受并发保护的删除同样在实际删除时校验预期条件。

例如业务代码决定将 `todo` 转为 `in_progress`，DAO 可以使用 `SET status = 'in_progress' WHERE id = ... AND status = 'todo'`，在写入时确认当前仍为 `todo`。如果操作只依赖这个当前状态，校验状态即可；如果决定还依赖其他字段或需要识别此前读取后发生的修改，则校验相应预期值、版本或 generation。条件必须覆盖所需保证，不能仅因采用乐观锁就统一增加版本字段。

采用版本号时，所有改变该版本所代表事实的写入入口，都必须按同一合同在实际修改时推进版本；无实际变化的成功空操作保留其既有版本语义。使用预期状态或字段值的条件写入，也要保留该资源已有的版本和时间更新合同。

对要求命中指定预期条件的单资源写入，影响零行表示条件未满足，必须按操作合同处理版本或状态冲突、记录不存在或其他条件不满足，不能报告成功。批量操作的零命中或幂等删除等另有完成语义的操作，遵循各自合同。调用方提供的预期值必须原样用于校验，不能先读最新值替换它，再覆盖并发修改。冲突默认返回调用方；仅对合同明确允许重新计算的内部操作进行有界重试，每次重新读取事实、计算候选并复核权限，不能原样重放陈旧决定。提交结果未知按完成合同处理，不能作为普通条件冲突重试。

乐观并发控制必须覆盖业务决定所依赖的全部可变事实。涉及权限、关联记录、多行或集合条件时，仅比较目标行的状态或版本未必足够；必须证明相关并发变化会被原子条件、覆盖该范围的版本或必要的唯一性保证阻止。仅把其他行的查询或预期值条件写在同一 SQL 中，并不自动阻止这些行或集合被并发修改。普通事务或只读快照本身不能替代这项证明。

悲观锁作为有明确理由的例外。确需使用 `SELECT ... FOR UPDATE`、advisory lock 等机制时，设计须说明乐观条件写入为何不足或不适合当前操作，以及保护的事实、参与写入入口、锁定对象和持有范围；以冲突或重试成本为理由时，提供实测依据。锁住必要的最小集合，缩短持有时间，保持一致的获取顺序，并让锁等待接受取消与 deadline。只读查询按所需快照读取，不为一般一致性读取增加排他锁。

乐观锁仍依赖数据库写入锁和事务，并不保证写入不等待；具体行为见 PostgreSQL 的[事务隔离](https://www.postgresql.org/docs/18/transaction-iso.html)与[锁机制](https://www.postgresql.org/docs/18/explicit-locking.html)说明。进程内 mutex 也不能替代多个服务实例之间的数据库并发控制。调整既有锁方案时，必须证明新的预期条件覆盖原来保护的全部不变量，保留原子性、权限、快照和失败语义；不能只移除加锁语句。

## 事务内决策与失败语义

业务判断可以基于读到的状态计算候选，但必须在实际写入时通过原子条件校验所依赖的事实仍成立，或在必要的悲观锁范围内重新读取并判断。事务外读取的状态未经并发校验，不能直接作为受并发影响的写入依据。条件写入、版本比较以及 lease 或 generation 校验，属于保持原子性所需的存储机制。

具体操作遵守所属领域的隔离级别和快照合同；需要悲观锁的路径还须遵守锁顺序。依赖数据库时间的操作，从事务作用域取得所需的时间；既有合同要求锁后取时的，必须保留该顺序。业务代码决定时间的用途，数据库提供合同约定的时间事实。

提交结果区分 `committed`、`not_committed` 和 `unknown`。提交确认丢失不能解释为已回滚，也不能仅凭 `unknown` 自动重放写入；恢复遵循所属操作的幂等与核对合同。查询、锁等待和事务执行传递 context 取消与 deadline；回滚和关闭遵守所属操作的清理预算，保留原始错误链及清理失败。

文件、网络及连接等外部副作用仍由相应流程拥有，明确执行顺序和失败处理；数据库事务不能替代这些资源的完成证明。

## 数据格式、迁移与错误

存储格式使用明确的字段类型与可空语义；数据访问映射不承担业务数据修复。无效的持久化数据必须暴露错误，不得静默补默认值、截断、丢弃字段或跳过记录。

JSON 和协议数据由所属代码校验与解码。不要为兼容历史坏数据或绕过容量问题，在 SQL 中重建一套 JSON 解码、字段匹配或日期解析规则。先明确支持的 API、导入入口和容量合同；存储格式变化由迁移处理，在线读取遵守明确的拒绝与错误语义。

迁移属于 DAO 实现，保持 schema、数据转换和迁移账本的原子性。已应用历史迁移及其校验身份不得随当前业务规则调整而重写。新库初始化、既有库升级、schema snapshot 维护和失败检查遵循 [Server README](../packages/daynight-server/README.md#schema-snapshot-maintenance)及[服务架构](design/daynight-server.md#启动迁移与关闭)的既有机制。

## 查询、索引与性能

查询按实际需要选择字段，避免为了少写代码而读取大正文或完整 JSON。返回范围、分页、批量大小与取消行为应符合业务容量合同；有界返回不能掩盖无界的取回或应用层物化。

索引应服务明确的过滤、关联、排序或唯一性需求。新增前核对现有索引及主键、唯一约束建立的索引，避免重复维护。评估查询收益时同时考虑写入、存储和锁定成本；移除索引也要核对其查询与并发用途。

对复杂或已观察到成本的路径，检查实际执行计划、数据规模、并发和写入频率。性能收益使用可比较负载下的测量表达；约束数量、SQL 行数或单次耗时不能直接证明瓶颈，也不能换算成整体收益。

## 审查要点

- 业务决策是否留在所属模块，SQL 是否只执行其数据访问与原子性职责？
- SQL 必须执行的筛选和排序是否符合领域合同，并保持分页、容量和查询次数？
- 每个约束和索引是否有明确保证或查询用途，是否重复执行业务校验？
- 是否优先使用乐观锁，并原子校验全部相关事实？悲观锁是否有明确理由、最小范围和一致顺序，冲突是否按合同处理？
- 读取、判断与写入是否保留所需事务、快照、权限、版本、时间及失败语义？
- schema 或规则归属调整是否覆盖全部写入入口，并通过迁移及所属层测试保持保证？
- 性能结论是否有对应负载和观察依据，错误与提交结果是否被如实保留？
