# Agent Note: Exact Application CORS for User REST

Status: implemented

## Problem

An application browser calling user REST needs to read authenticated success and
failure responses together with Worker and Session protocol headers. Authentication
and path rejection can happen before a business handler, so individual handler
headers cannot provide consistent browser-visible errors. Preflight must describe
real user routes without invoking authentication, user initialization or business
operations.

## Decision

The HTTP composition wraps ordinary authentication and PathGuard with a user REST
CORS adapter. Its configuration owns `s2s.allowed_origin` and
`DAYNIGHT_S2S_ALLOWED_ORIGIN`: one canonical exact HTTPS origin, with an explicit
loopback HTTP exception under the existing HTTP test-origin policy. An explicit
empty setting disables this browser response capability without changing no-Origin
REST authentication, internal issuance or public refresh. An absent environment
variable preserves the YAML value; an explicit empty or nonempty value replaces
it. The supplied localhost and dev-ci Compose configurations preserve environment
presence rather than synthesizing an empty override. The blank localhost
environment template entry deliberately selects disabled browser CORS unless
the host environment overrides it. Startup rejects malformed and noncanonical
values before opening business resources.

Allowed-Origin responses echo that exact origin and merge Vary. Credential-free
OPTIONS probes the actual HTTP mux registration without running its handler,
then checks the explicit request-header allowlist. Most methods come directly
from typed mux patterns. Narrow adapter rules describe the existing methodless
Bot and Webhook dispatchers and preserve literal Task search and Session HEAD
refusals. The adapter exposes the necessary identity, request, version, download,
negotiation and Worker headers while preserving downstream header values and
parsers. The
[authentication design](../../../../docs/design/daynight-auth.md#用户-rest-的精确-cors)
owns the complete tables and externally observable behavior.

CORS supplies no authentication or resource authority and sends no
Access-Control-Allow-Credentials. Native Cookie mutation requires the exact main
site Origin; account-root and producer credentials retain their existing checks.
Method-specific producer classification excludes archive POST/PUT writes,
upload preparation and writer upload receipts. Preparation and writer-status
GETs still use the original PAT-owner upload admission. Their OPTIONS returns
credential-free 403 without CORS headers, authentication or upload reservation.
User archive root/status, content and file-byte reads, and user image uploads
retain user CORS. Controller and Worker producer channels remain excluded.
The S2S issuer path is excluded. Public OAuth and MCP retain their independent
CORS; static assets and health routes retain their existing behavior. API token
issuance, REST credential admission and browser WebSocket authentication are
separate mechanisms.

## Alternatives

**Add headers inside each business handler.** Authentication, PathGuard, router
404 and method errors can finish before those handlers execute. Repeating policy
across handlers would leave those errors unreadable and create multiple header
owners.

**Copy every route into a separate preflight catalog.** A complete duplicate
can drift from mux registrations and accidentally advertise unsupported user
operations. Typed routes use the actual mux patterns. Methodless dispatchers,
existing refusal patterns and method-specific producer admission need narrow
adapter rules; those rules retain a
small synchronization obligation without replacing the router.

**Allow all origins, headers or credentials.** A wildcard would discard the single
configured application boundary. Credentialed cross-origin responses would mix
native browser sessions with the application response capability. Producer headers
would advertise capabilities that user credentials do not grant.

## Consequences

Application browsers can read the original REST result and protocol metadata even
when authentication, path checks or resource operations fail. Preflight proves
route and header compatibility without creating an account or running business
work. Existing value, duplicate, version and capacity checks remain at their
original owners.

The exact origin requires a restart when changed. Request and exposed-header
allowlists must stay synchronized with supported user protocol headers. Changes
to methodless Bot/Webhook dispatchers, explicit refusal patterns or producer
admission must also update their narrow preflight rules. CORS does
not make a denied request succeed, enable the S2S issuer in a browser, grant
producer authority or change native session privacy.
